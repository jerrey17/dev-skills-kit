思维框架内容: |
  # 业务模拟验证思维框架 (Simulation & Verification)

  > **文档定位**：业务模拟验证是一套针对业务需求文档的**逻辑验真机制**。通过结构化的沙盘推演，深度扫描自然语言描述的需求，识别并消除逻辑漏洞、边界缺失及数据流断层，确保业务功能文档的**完备性**与**合理性**。

  ---

  ## 1. 输入与产出 (I/O)

  ### 1.1 输入源

  | 输入文档 | 核心内容 | 模拟验证中的作用 |
  | :--- | :--- | :--- |
  | **业务功能文档** | 业务流程、角色定义、属性描述、业务规则 | 提供验证的**原始素材**和**逻辑准则** |

  ### 1.2 产出物

  1.  **场景知识图谱**：包含全量角色、对象、属性及其关联关系的结构化描述。
  2.  **结构化场景描述**：包含场景定义、角色实例、对象实例及其初始状态的文本化对象模型。
  3.  **推演执行日志**：详细记录每一步操作、状态变更及校验结果。
  4.  **逻辑阻断报告**：发现的需求漏洞、矛盾点或定义缺失清单。

  ---

  ## 2. 基础层：设计哲学 (Why)

  ### 2.1 核心挑战
  *   **语义歧义**：自然语言描述容易产生歧义，导致实现偏差。
  *   **逻辑漏洞**：复杂的业务流程中隐藏着死循环、逻辑死锁或资源不守恒问题。
  *   **定义缺失**：需求描述往往关注“正常路径”，忽略了异常边界和属性的完整定义。

  ### 2.2 设计原则
  *   **逻辑验真**：在零成本阶段发现设计缺陷，而非在编码后。
  *   **数据守恒**：业务推演必须满足物理守恒规律（如：出账额 = 入账额 + 费用）。
  *   **原子化推演**：将业务动作拆解为可执行的原子操作，逐一校验连通性。

  ---

  ## 3. 概念层：核心理论 (What)

  ### 3.1 核心概念
  *   **沙盘推演**：在逻辑虚拟机中，按预定顺序装载业务场景并执行。
  *   **静态建模**：将自然语言场景实例化为结构化对象网络。
  *   **动态推演**：依照业务规则算法驱动流程流转，观察状态变更。
  *   **一致性规则**：定义状态流转和属性联动的硬性约束。

  ### 3.2 概念关系
  *   **输入**驱动**静态建模**，**静态建模**提供**推演基础**，**动态推演**产出**验证结果**。

  ---

  ## 4. 方法层：实践指南 (How)

  为了构建高质量的业务逻辑模型，需遵循以下四个核心步骤进行推演。

  ### 第一步：目标定位 (Goal Analysis)

  **步骤描述**：
  对业务功能文档进行全景扫描，深度分析其业务背景、核心目标及功能范围。通过抽象与提炼，明确系统"是什么"以及"做什么"，从而划定清晰的业务边界，为后续的场景梳理提供顶层准则。

  **执行动作**：
  1.  **背景解析**：识别业务产生的动因（Why），理解解决的核心痛点。
  2.  **职责抽象**：用标准化的语言提炼系统的核心职能（What），明确其服务对象及关键能力。
  3.  **边界划定**：明确系统管辖的范围（Scope），区分核心业务与外部依赖，确立场景梳理的“围栏”。

  **核心产出**：
  *   **系统定位陈述**：一句标准严谨的定义。（例如：“这是一个面向个人借款人，提供从实名签约、额度授信、资金发放至本息偿还全生命周期管理的信贷核心系统。”）

  ### 第二步：业务规则分析 (Rule Extraction)

  **步骤描述**：
  基于系统定位，对业务文档进行全量扫描与深度抽象，构建该业务场景的**核心知识图谱**。此步骤要求穷尽所有参与业务的实体及其属性，并严格定义实体间的交互规则，确保在逻辑层面实现数据的**一致性**与**守恒性**。

  **执行动作**：
  1.  **全量要素抽象**：
      *   **角色与对象**：识别所有显性与隐性参与者（如借款人、账户、订单、资金池）。
      *   **属性定义**：为每个实体建立详细的属性列表（如：账户不仅有余额，还有状态、冻结金额、币种），确保信息维度的完备性。
  2.  **一致性规则构建**：
      *   定义业务场景下的**状态流转图**（State Transition）。
      *   确立属性变更的**联动逻辑**（如：“转账”场景下，必须满足 A账户减少额 = B账户增加额），保证业务内部的数据一致性。

  **核心产出**：
  *   **场景知识图谱**：包含全量角色、对象、属性及其关联关系的结构化描述。
  *   **一致性规则集**：明确定义的状态变更逻辑与数据守恒准则。

  ### 第三步：静态建模 (Static Modeling)

  **步骤描述**：
  在虚拟的逻辑空间中，通过文字构建**对象化、结构化**的业务全景。这一步类似于编程中的“实例化”过程，要求用严谨的结构化描述（类 JSON 或 YAML 风格）来初始化所有对象、角色及其关系（依赖、顺序等），确保模型内部的**一体性**，防止后续模拟中出现数据断层或逻辑损坏。

  **执行动作**：
  1.  **场景对象化**：
      *   将自然语言描述的业务场景转化为**结构化对象**（Scenario Object）。
      *   明确场景的前置依赖（Pre-conditions）和内部执行顺序（Sequence）。
  2.  **实例初始化**：
      *   根据第二步的知识图谱，**实例化**所有参与的角色与对象。
      *   赋予每个实例精确的**初始状态值**（Initial State），确保所有属性在推演开始前具备确定的数值或状态。
  3.  **关系网络构建**：
      *   定义实例之间的引用关系（如：订单对象内部包含用户ID和商品ID），形成逻辑闭环。

  **核心产出**：
  *   **结构化场景描述**：一份包含场景定义、角色实例、对象实例及其初始状态的文本化对象模型（Text-based Object Model）。

  ### 第四步：动态推演 (Dynamic Execution)

  **步骤描述**：
  在逻辑虚拟机中，按预定顺序装载业务场景，将静态初始化的角色与对象**投射**（Project）入场，并严格依照既定规则算法驱动流程流转。此步骤的核心旨在验证**业务逻辑的闭环性**。要求所有操作不仅物理可执行，且在业务层面上必须**合规**与**成功**。

  **执行动作**：
  1.  **场景装载与投射**：
      *   选定当前要执行的业务场景（如“放款”）。
      *   将静态建模中的角色实例（如出借人账户）与对象实例（如借据）传入场景上下文。
  2.  **原子化执行**：
      *   按序调用业务规则算法（如“执行扣款指令”）。
      *   **连通性校验**：检查执行所需的**前置依赖**是否物理存在（例如：必须存在“出款账户”对象，必须存在“余额”属性）。
  3.  **规则执行与校验**：
      *   **执行**：按序调用业务规则算法。
      *   **双重校验**：
          *   **物理校验**：检查对象、属性是否存在（可执行性）。
          *   **逻辑校验**：检查变更后的状态是否符合业务常识（如：余额不为负、状态流转合法）。
  4.  **结果判定**：
      *   若出现任何物理缺失或逻辑违规（如扣成负数），均视为**推演失败**。这通常意味着初始数据设定错误或规则设计存在漏洞，需回头修正。

  **核心产出**：
  *   **推演执行日志**：记录每一步的调用栈、参与对象及执行结果状态（成功/中断），直至完成全链路业务场景。
  *   **逻辑阻断报告**：若推演中断，详细记录缺失的条件或无法调用的规则。

  ## 5. 实施层：标准 SOP 实现案例 (Example)

  本章节以**“信贷放款核心流程”**为例，展示一套完整的沙盘推演范本。我们将模拟一个名为“助农贷”的业务场景，验证从资金划拨到借据生成的全链路逻辑。

  ### 5.1 第一步：目标定位 (Goal Analysis)

  **系统定位陈述**:
  > “这是一个面向农户的信贷核心子系统，负责在授信额度内，将资金方（银行）的资金安全、准确地划拨至借款人（农户）账户，并同步生成具有法律效力的债权凭证（借据），实现资金流与信息流的原子性交付。”

  ### 5.2 第二步：业务规则分析 (Rule Extraction)

  **业务要素清单 (Schema)**:

  ```yaml
  # 1. 角色定义 (Actors)
  Borrower (借款人):
    - id: String         # 唯一标识
    - wallet_bal: Decimal # 钱包余额 (用于收款)
    - credit_limit: Decimal # 剩余授信额度 (用于风控)

  Funder (资金方):
    - id: String
    - pool_bal: Decimal   # 资金池余额 (用于出资)

  System (核心系统):
    - fee_account: Decimal # 平台手续费账户

  # 2. 业务对象 (Objects)
  LoanReceipt (借据):
    - receipt_no: String  # 借据号
    - principal: Decimal  # 借款本金
    - state: Enum [INIT, ACTIVE, OVERDUE, SETTLED] # 借据状态

  # 3. 业务场景规则 (Scenario Rules)
  Action_Disburse (放款动作):
    Input: [amount, fee_rate]
    Logic:
      1. fee = amount * fee_rate
      2. Borrower.credit_limit -= amount
      3. Funder.pool_bal -= amount
      4. Borrower.wallet_bal += (amount - fee)
      5. System.fee_account += fee
      6. LoanReceipt.state = ACTIVE
  ```

  **一致性规则集 (Consistency Rules)**:
  1.  **额度互斥规则**: 放款金额 <= 借款人剩余授信额度。
  2.  **资金守恒公式**: `资金方出资额` = `借款人到账额` + `平台手续费`。
  3.  **借据生效条件**: 仅当资金成功到账后，借据状态才可由 `INIT` 转为 `ACTIVE`。

  ### 5.3 第三步：静态场景初始化 (Static Setup)

  **结构化场景描述 (Scenario Snapshot)**:

  ```yaml
  Scenario: "HappyPath_01_正常全额放款"
  Description: "农户张三申请借款1000元，资金方资金充足，费率1%。"

  # 实例初始化 (Instance Initialization)
  Instances:
    # 借款人: 张三
    farmer_zhang (Borrower):
      id: "USR_zhang"
      wallet_bal: 50.00      # 初始有点零钱
      credit_limit: 5000.00  # 额度充足

    # 资金方: 某村镇银行
    bank_rural (Funder):
      id: "FND_rural"
      pool_bal: 100000.00    # 资金池充裕

    # 平台账户
    sys_platform (System):
      fee_account: 0.00

    # 待生成的借据 (预置状态)
    receipt_new (LoanReceipt):
      receipt_no: "L_20231001"
      principal: 1000.00     # 申请金额
      state: "INIT"          # 初始态

  # 关系绑定
  Relations:
    receipt_new.owner -> farmer_zhang.id
    receipt_new.funder -> bank_rural.id
  ```

  ### 5.4 第四步：动态推演 (Dynamic Execution)

  **推演执行日志 (Runtime Log)**:

  | 序号 | 步骤名称 | 调用栈 (Action) | 状态变更详情 (Mutation) | 校验结果 (Validation) |
  | :--- | :--- | :--- | :--- | :--- |
  | **01** | **额度校验与扣减** | `Borrower.occupyQuota(farmer_zhang, 1000)` | `credit_limit`: 5000 -> 4000 | ✅ **PASS**<br>物理: 属性存在<br>逻辑: 剩余额度充足 |
  | **02** | **资金方扣款** | `Funder.debit(bank_rural, 1000)` | `pool_bal`: 100000 -> 99000 | ✅ **PASS**<br>物理: 资金池对象存在<br>逻辑: 余额 > 0 |
  | **03** | **费用计算** | `System.calcFee(1000, 1%)` | `temp_fee` = 10.00 | ✅ **PASS** |
  | **04** | **借款人入账** | `Borrower.deposit(farmer_zhang, 990)` | `wallet_bal`: 50.00 -> 1040.00 | ✅ **PASS**<br>逻辑: 入账额 = 本金 - 手续费 |
  | **05** | **手续费归集** | `System.income(sys_platform, 10)` | `fee_account`: 0.00 -> 10.00 | ✅ **PASS** |
  | **06** | **借据生效** | `LoanReceipt.activate(receipt_new)` | `state`: INIT -> ACTIVE | ✅ **PASS**<br>逻辑: 前置资金流转已完成 |

  **推演总结**:
  *   **资金守恒检查**: 出 (1000) == 入 (990 + 10)。结果: **平衡**。
  *   **最终结论**: ✅ **逻辑闭环，推演成功**。

  ### 5.5 异常阻断示例 (Blocker Showcase)

  **场景**: 假设初始化时，借款人 `credit_limit` 仅为 500 元。

  | 序号 | 步骤 | 调用栈 | 状态变更 | 结果判定 |
  | :--- | :--- | :--- | :--- | :--- |
  | **01** | **额度校验与扣减** | `Borrower.occupyQuota(farmer_zhang, 1000)` | **无变更** | ❌ **FAIL (逻辑违规)**<br>原因: 申请金额(1000) > 剩余额度(500)，业务规则拦截。 |

  **场景**: 假设初始化时，忘记定义 `Funder` 的 `pool_bal` 属性。

  | 序号 | 步骤 | 调用栈 | 状态变更 | 结果判定 |
  | :--- | :--- | :--- | :--- | :--- |
  | **02** | **资金方扣款** | `Funder.debit(bank_rural, 1000)` | **无变更** | ❌ **BLOCK (物理缺失)**<br>原因: 对象 `bank_rural` 缺少 `pool_bal` 属性，无法执行扣减操作。 |

  ## 6. 质量标准

  - [ ] **全覆盖**：验证场景是否覆盖了所有核心业务路径及典型异常路径？
  - [ ] **自洽性**：业务逻辑是否在推演中实现了自我闭环？
  - [ ] **守恒性**：所有涉及资源流转的步骤是否满足守恒公式？
  - [ ] **追溯性**：每个推演失败点是否都能明确追溯到需求描述的具体缺陷？
