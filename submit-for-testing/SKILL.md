# submit-for-testing — 提测阶段

## 阶段目标

单元测试通过后，为测试团队提供完整的提测材料，包含两部分：
1. **发布 CheckList（面向测试环境）**：基于前面所有阶段产物及代码改动，梳理本次发布需要检查和确认的所有事项。**本章节面向测试环境部署**（给测试同学部署测试环境用）；生产发布的权威操作清单由 `release-checklist` 在 bug 修复闭环后产出（`09-发布CheckList.md`）。
2. **可测性分析**：对完整需求进行可测性评估，明确测试范围、测试条件和验收标准

产出文件：`workflow/{需求名称}/07-提测.md`

---

## 输入依赖

执行前必须读取以下已有产物：

| 文件 | 用途 |
|------|------|
| `workflow/{需求名称}/01-需求分析.md` | 功能清单、边界约束、验收条件 |
| `workflow/{需求名称}/02-服务拆分.md` | 涉及服务列表、改动范围 |
| `workflow/{需求名称}/03-技术方案.md` | 接口定义、数据结构、核心流程 |
| `workflow/{需求名称}/04-开发编码.md` | 任务完成情况、关键实现 |
| `workflow/{需求名称}/05-代码审查.md` | 审查结论、遗留问题 |
| `workflow/{需求名称}/06-单元测试.md` | 单元测试结果、已覆盖场景 |
| `.claude/workflow/{需求名称}/current.md` | 主项目路径、关联项目、PR 链接 |

---

## 执行步骤

### Step 1 — 读取所有前置产物

按上表依次读取文件，提取以下关键信息：
- 需求功能清单（来自需求分析）
- 涉及服务及改动范围（来自服务拆分）
- 新增/修改的接口列表（来自技术方案）
- 数据库变更（DDL、字段变更等，来自技术方案）
- 配置项变更（来自技术方案/开发编码）
- 代码审查遗留问题（来自代码审查）
- PR 链接（来自 current.md）

### Step 2 — 扫描代码改动（可选，有 git 仓库时执行）

若主项目路径存在本地 git 仓库，执行：
```bash
git -C {主项目路径} diff --name-only origin/main...HEAD
git -C {主项目路径} log --oneline origin/main...HEAD
```

提取：
- 变更文件列表（按模块分类）
- 提交摘要

### Step 3 — 生成发布 CheckList

基于前面收集的信息，生成结构化 CheckList：

```markdown
## 一、发布 CheckList

### 前置准备
- [ ] 代码审查已通过，无阻塞问题
- [ ] 所有相关 PR 已合并到发布分支
- [ ] 单元测试 / 集成测试全部通过
- [ ] 数据库变更脚本已准备（如有）
- [ ] 配置项变更已同步到各环境（如有）

### 服务变更确认
（按 02-服务拆分.md 中的服务列表逐项列出）
- [ ] {服务名}：{改动范围简述}，版本/分支：{PR或分支链接}
- [ ] ...

### 接口变更确认
（按 03-技术方案.md 中的接口列表逐项列出）
- [ ] {接口路径} [{HTTP方法}]：{新增/修改/废弃}，是否有向后兼容性
- [ ] ...

### 数据库变更确认
- [ ] DDL 脚本已在测试环境执行（如有）
- [ ] 涉及字段：{字段列表}
- [ ] 是否有历史数据迁移需求

### 配置项变更确认
- [ ] {配置项名}：{变更说明}（如无则填"无"）

### 依赖服务确认
- [ ] 上游服务接口版本兼容（如有依赖）
- [ ] 下游服务通知（如有影响）

### 发布顺序（多服务时）
按依赖关系列出发布顺序：
1. {服务名}（原因：{为什么先发这个}）
2. ...

### 回滚预案
- [ ] 回滚方案已明确：{简述回滚步骤}
- [ ] 回滚影响范围：{数据是否可逆、用户影响}
```

### Step 4 — 进行可测性分析

对完整需求逐项评估可测性：

```markdown
## 二、可测性分析

### 测试范围
根据功能清单，本次需求涉及以下测试范围：
| 功能点 | 测试类型 | 优先级 | 可测性评估 |
|--------|---------|--------|-----------|
| {功能点} | 接口测试 / UI测试 / 集成测试 | P0/P1/P2 | 可测 / 需补充条件 / 不可测 |

### 测试前置条件
列出开始测试前必须满足的条件：
- **环境要求**：{测试环境、数据库版本、依赖服务}
- **测试数据**：{需要预置的数据，如测试账号、初始化数据}
- **权限要求**：{测试账号需要的权限}
- **依赖 Mock**：{哪些外部依赖需要 Mock，预期返回值}

### 核心验收标准
对每个主要功能点给出明确的验收条件（可直接用于测试用例）：

#### {功能点1}
- 正常路径：{输入 X → 预期输出 Y}
- 边界条件：{边界值列表}
- 异常路径：{输入异常 → 预期错误响应}

#### {功能点2}
...

### 不可测项 / 测试盲区
列出本次无法有效覆盖的场景及原因：
| 场景 | 无法测试原因 | 风险等级 | 建议 |
|------|------------|---------|------|
| {场景描述} | {原因} | 高/中/低 | {补偿措施} |

### 性能 / 压力测试需求
- [ ] 本次改动涉及高频接口，建议压测：{接口路径，预期 QPS}
- [ ] 无性能测试需求

### 回归范围建议
除新功能外，建议回归以下已有功能：
- {功能点}（原因：{与本次改动的关联}）
```

### Step 5 — 汇总代码审查遗留问题

从 `05-代码审查.md` 提取未解决的问题，列入提测文档：

```markdown
## 三、遗留问题清单

| 编号 | 问题描述 | 严重程度 | 处理状态 | 备注 |
|------|---------|---------|---------|------|
| 1 | {问题} | 阻塞/非阻塞 | 已修复/待修复/接受风险 | {说明} |
```

如无遗留问题，填写"无遗留问题"。

### Step 6 — 写入产出文件

将以上三部分内容合并，写入：
```
workflow/{需求名称}/07-提测.md
```

文件头部加入提测摘要：
```markdown
# {需求标题} — 提测文档

- **需求 TAPD ID**：{ID 或 N/A}
- **生成时间**：{当前日期}
- **提测人**：{从 current.md 读取处理人，或留空}
- **目标测试环境**：{从用户确认，默认填"待确认"}
- **预计提测时间**：{从用户确认}
- **涉及服务**：{服务列表，来自 02-服务拆分.md}
```

### Step 7 — 等待用户补充信息

在生成文档前，询问用户以下信息（可跳过，留空后补）：
1. 目标测试环境（如 fat / uat）
2. 预计提测时间
3. 是否有特殊测试要求或已知限制

### Step 8 — 追加「小结」段落（必写）

在 `07-提测.md` 文件末尾追加 `## 小结` 段落，3 个固定 bullet。独立调用时也写（作为提测文档小结，非 dev-workflow 专属）：

```markdown
## 小结

- 产出: {文件清单，如 workflow/XX/07-提测.md}
- 阻塞: {无，或简述；如"2 项遗留问题待测试同学确认接收"}
- 交接: {一句话，下一阶段必须知道的；如"提测涉及 3 服务 8 接口，测试同学已确认接收"}
```

**字段规则**：
- `产出`：本阶段产出的所有文件路径
- `阻塞`：三、遗留问题清单中未解决项；无则写"无"
- `交接`：服务数 + 接口数 + 测试同学接收情况（一句话）

### Step 9 — 面向用户的结束语

完成后输出一句话摘要：
```
提测文档已生成，涉及 {N} 个服务、{M} 个接口，包含 {K} 项 CheckList 和 {L} 个功能点可测性分析。
```

## 审核要点

提测文档完成后，向用户展示：
```
✅ 提测阶段已完成，产出：workflow/{需求名称}/07-提测.md

请审核提测文档，确认无误后提交测试团队。
重点检查：CheckList 是否覆盖所有服务变更、验收标准是否可操作

下一阶段：bug修复
测试同学开始测试后，处理反馈的问题：定位 → 根因分类 → 修复带单测 → 回归闭环

确认后如何继续？
  · 输入「确认，进入下一阶段」→ 提测文档审核通过，进入 bug 修复阶段
  · 输入「有问题：{描述}」→ 根据反馈修正文档后重新提示
  · 输入「先暂停」→ 保存进度，稍后继续
  · 输入「跳到 XX 阶段」→ 直接跳转（跳过审核）
```
