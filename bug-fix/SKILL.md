# bug-fix — bug 修复

## 使用场景

dev-workflow bug修复阶段（提测之后、发布CheckList 之前）调用，处理三类来源的问题：

1. **TAPD bug 单**：测试同学提单（有 bug ID）
2. **测试群/口头反馈**：需先结构化登记
3. **预发/生产拦截**：预发环境或生产验证发现的问题

本阶段是**循环阶段**：新 bug 随时进来，逐个走"登记 → 定位 → 修复 → 回归"闭环。核心原则：**先证据后结论，禁止凭直觉改代码**。

## 输入参数

| 参数 | 说明 |
|------|------|
| 需求名称 | 用于定位产物目录 |
| 主项目路径 | 源码定位路径 |
| 正式产物目录 | `workflow/{需求名称}/` |
| bug 来源 | TAPD bug ID / 口头描述 / 预发生产反馈 |

## 执行步骤

### Step 1 — 接入与登记

- 有 TAPD bug ID → 调 `mcp__tapd__get_bug` 拉取详情（标题/描述/严重程度/复现步骤）
- 口头反馈 → 整理为结构化记录：**现象 / 环境（测试/预发/生产）/ 复现路径 / 预期 vs 实际 / 影响范围**
- 登记到 `08-bug修复.md` 的 bug 清单，状态 = `待定位`

环境判定很重要：同一个现象在测试/预发/生产的根因可能完全不同（环境差异类问题的典型特征）。

### Step 2 — 定位（先证据后结论）

按以下顺序取证，每一步留证据（日志片段/查询结果/代码位置）：

1. **日志实证**：test/production 日志查询 MCP（appid 必参），按 trace_id / 关键词查证实际传参与行为。先实证"系统实际收到了什么、做了什么"，再下结论
2. **区分代码 vs 配置**：传参正常但展示/流程异常 → 优先怀疑配置或流程表单定义（如 OA 审批表单显示条件），不要盲目改代码
3. **数据验证**：只读核对库表数据，禁止写库。映射/兜底类方案先验证数据充分性（映射表是否有空洞），数据验证可以当天推翻错误方案，比代码评审快
4. **外部依赖可达性**：涉及外部域名/老服务时，先验证该依赖在当前环境可达（测试环境依赖不可达会误判为代码 bug）
5. **白盒分析**：`gitnexus_query` / `gitnexus_context` 定位调用链；确认要改后 `gitnexus_impact` 评估影响面

### Step 3 — 根因分类

每个 bug 必须归入以下一类或多类（复盘阶段直接消费此分类）：

| 根因分类 | 典型特征 |
|---------|---------|
| 契约遗漏 | 上游接口的强制入参/环境差异/数据权限语义未调研（只看了"返回什么"没看"强制什么"） |
| 边界未穷尽 | 全失败无兜底（空 zip 假成功）/ 空值 / 分页 / 超限分支未覆盖 |
| 协议字段缺失 | proto 加了字段但没重生成 / PB 序列化丢字段 / 映射遗漏 |
| 注释与实现脱节 | 注释写"名称"实现塞 code，展示口径与明细不同源 |
| 配置不一致 | 跨服务共享资源（桶/Topic/白名单）配置两端不一致；环境配置缺失 |
| 环境差异 | 测试宽松生产严格；测试环境依赖不可达掩盖问题 |
| 非代码问题 | 配置/流程定义/数据问题，无需改代码（实证后归此类） |
| 原型偏差 | 产品原型与实现细节的正常迭代（字段口径/展示细节） |

### Step 4 — 修复（约束）

- **影响面先行**：改任何 symbol 前 `gitnexus_impact(direction: upstream)`，HIGH/CRITICAL 风险必须向用户报告
- **修复范围**：局限在新代码内，老链路零影响（新老分流约束给了这个底气，不要破坏它）
- **必须带单测**：修复的边界分支显式覆盖，防止"修一个引一个"
- **PB 加字段三件套**：proto 定义 + protoc 基线重生成 + 映射回归测试，缺一不可
- **降级路径兜底**：catch 后继续的降级路径必须回答"全失败时状态是什么、用户看到什么"；warn 日志含根因（异常类名+堆栈），禁止吞成模糊文案
- **DB 写操作**（UPDATE/INSERT/DELETE/DDL）：先给 SQL + 影响范围 + 回滚方案，**用户明确授权后才执行**
- **commit 后不主动 push**：告知用户修复内容 + commit 号 + **部署范围**（哪些服务需重新部署、一仓多部署单元需全部列出），等用户确认
- **需求变更识别**：测试期发现的"非 bug 类调整"（产品临时改口径/改范围）→ 转 dev-workflow 需求变更流程（变更影响矩阵），不在本 skill 内直接改

### Step 5 — 回归闭环

1. 单测全绿
2. 告知用户部署范围，用户确认后部署到测试环境
3. 通知测试同学回归（说明修复点 + 建议回归路径）
4. 有 TAPD bug 单的，`mcp__tapd__update_bug` 流转状态 / 添加修复说明评论
5. 更新 bug 清单状态：`待定位 → 定位中 → 修复中 → 待回归 → 已闭环`

### Step 6 — 维护产出文件

`08-bug修复.md` 随修复进度持续更新，结构：

```markdown

| 1 | 11387... | 大类筛选漏返合同 | 测试 | 契约遗漏 | proto 无 major_category 字段 | 77637c64 | +3 | 已闭环 | api.atm |

- 产出: workflow/{需求名称}/08-bug修复.md
- 阻塞: {无，或未闭环 bug 简述}
```

**两个下游消费关系**（必须维护，是本阶段的核心交接）：
- 「三、配置类问题回填清单」→ `release-checklist` 生成「我要操作的」/「我要关注的」时直接消费
- 「四、根因归纳」→ 复盘阶段"问题根因归纳"章节直接消费

### Step 7 — 退出条件

满足其一即可退出本阶段，进入发布CheckList：
- TAPD 侧本需求 bug 全部已解决/已验证，无 open bug
- 当前批次 bug 全部闭环 + 用户确认可发布

退出时向用户汇报：bug 总数 / 已闭环 / 未闭环（含原因）/ 回填 CheckList 项数。
