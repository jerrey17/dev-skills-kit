思维框架内容: |
  # 测试思维框架

  > **核心理念**：测试设计的本质是**场景穷举**——运用逻辑思维，系统性地识别和推导出所有可能的场景，确保软件质量的全面覆盖。
  >
  > **文档定位**：本框架以**测试工程师**的专业视角，指导如何基于业务功能文档和架构设计文档，设计出逻辑严密、覆盖全面的测试清单。

  ## 0. TDD Red-Green-Refactor 循环

  > **Iron Law: NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST**

  测试设计不仅是"穷举场景"，更是一种开发纪律。推荐遵循 TDD 循环：

  ```
  RED   →  写一个最小失败测试，描述期望行为
  GREEN →  写最少代码让测试通过
  REFACTOR → 清理代码，保持测试绿色
  ```

  ### RED 阶段要求

  <Good>
  ```java
  @Test
  void test_cancel_whenPending_shouldChangeStatusToCanceled() {
      // Given
      Order order = new Order("order1", OrderStatus.PENDING);
      // When
      order.cancel();
      // Then
      assertEquals(OrderStatus.CANCELED, order.getStatus());
  }
  ```
  清晰命名，测试真实行为，一次只验一件事
  </Good>

  <Bad>
  ```java
  @Test
  void testCancel() {
      Order order = mock(Order.class);
      when(order.cancel()).thenReturn(true);
      assertTrue(order.cancel());
  }
  ```
  模糊命名，测试的是 mock 行为而非真实逻辑
  </Bad>

  ### GREEN 阶段要求

  写最简代码让测试通过。不要过度设计、不要添加当前测试未要求的功能。

  ### REFACTOR 阶段要求

  只在测试全绿后进行。移除重复、改善命名、提取辅助方法。不增加新行为。

  ### Common Rationalizations（常见自我合理化）

  | 借口 | 现实 |
  |------|------|
  | "太简单了不需要测试" | 简单代码也会出错。测试只需 30 秒。 |
  | "我之后再补测试" | 后补的测试立即通过，证明不了任何事。 |
  | "手动测试过了" | 手动测试是临时的，无法重复运行，无法证明边界覆盖。 |
  | "删掉 X 小时的代码太浪费了" | 沉没成本谬误。保留未经验证的代码才是技术债。 |
  | "留着当参考，先写测试" | 你会改编它而不是重写，这就是 test-after。删除即删除。 |
  | "TDD 太教条了，我比较务实" | TDD 就是务实的：编码前发现 bug 比编码后调试更快。 |
  | "后补测试能达到一样效果" | 后补测试回答"代码做了什么"，先写测试回答"代码应该做什么"。 |
  | "先探索一下再写测试" | 可以探索，但探索代码必须丢弃，然后用 TDD 重写。 |
  | "测试太难写说明设计没问题" | 测试难写 = 接口难用。倾听测试的反馈，简化设计。 |
  | "现有代码没有测试" | 你在改进它。为现有代码补充测试，然后新代码用 TDD。 |
  | "手动测试更快" | 手动测试无法证明边界覆盖。每次变更都要重新手动测试。 |

  ### Red Flags -- 出现以下信号时立即停止并回溯

  - 先写了实现代码再补测试
  - 测试一写出来就立即通过（没有观察到 RED 阶段）
  - 无法解释测试为什么失败
  - 测试是"后来加的"
  - 在合理化"就这一次跳过 TDD"
  - 说"我已经手动测试过了"
  - 说"后补测试能达到一样的目的"
  - 说"重要的是精神不是形式"
  - 说"留着当参考"或"改编一下现有代码"
  - 说"已经花了 X 小时，删掉太浪费"
  - 说"这次不一样因为..."

  **所有这些信号意味着：删除实现代码，从 TDD 重新开始。**

  ### When Stuck（卡住时的解法）

  | 问题 | 解决方案 |
  |------|----------|
  | 不知道怎么写测试 | 先写你期望的 API 调用方式，再写断言，最后补充 Given。 |
  | 测试太复杂 | 被测代码设计太复杂。简化接口。 |
  | 必须 mock 所有东西 | 代码耦合过重。使用依赖注入解耦。 |
  | 测试 setup 太长 | 提取辅助方法。仍然复杂？简化被测设计。 |
  | 不确定该测什么 | 回到行为规格（SPEC-），每条规格对应至少一个测试。 |

  ## 0.1 TDD 反模式分类

  ### Anti-Pattern: The Liar（说谎者）

  测试通过了但实际验证的不是预期行为。通常由模糊命名或错误断言导致。

  **信号**: 测试名与断言内容不匹配；修改业务逻辑后测试仍然通过。

  ### Anti-Pattern: The Mockery（过度 Mock）

  测试中 mock 设置代码超过了实际测试逻辑，测试验证的是 mock 行为而非真实行为。

  **信号**: mock 设置行数 > 断言行数 2 倍以上；删除被测代码后测试仍通过。

  ### Anti-Pattern: The Inspector（窥探者）

  测试过度耦合实现细节（私有方法调用顺序、内部数据结构），导致重构即破坏测试。

  **信号**: 测试中出现反射访问私有字段；方法签名不变但内部重构后测试失败。

  ### Anti-Pattern: The Giant（巨人）

  单个测试方法验证了过多行为，无法从失败信息中定位问题。

  **信号**: 测试方法名包含"and"；单个 @Test 方法超过 30 行断言逻辑。

  ### Anti-Pattern: The Free Rider（搭便车）

  测试没有自己的断言，完全依赖其他测试的执行顺序来验证正确性。

  **信号**: @Test 方法中无 assert/verify 语句；去掉此测试不影响覆盖率。

  ### Anti-Pattern: The Secret Catcher（暗中捕获）

  测试通过 try-catch 吞掉了异常，预期失败的场景静默通过。

  **信号**: 测试中有 catch 块但无 fail()；使用 assertDoesNotThrow 包裹应该抛异常的调用。

  ### Anti-Pattern: The Enumerator（无意义编号）

  测试方法名使用 test1、test2、test3，无法从名称判断测试场景。

  **信号**: 方法名中只有数字编号；不看代码无法理解测试目的。

  ### Anti-Pattern: Generous Leftovers（数据残留）

  一个测试创建了持久化数据，另一个测试隐式依赖这些数据。执行顺序改变时测试失败。

  **信号**: 测试单独运行失败但整体运行通过；测试依赖 @TestMethodOrder 固定顺序。

  ### Anti-Pattern: The Nitpicker（过度精确匹配）

  测试断言了完整的输出结构，但实际只关心其中个别字段。不相关字段的变更导致测试频繁失败。

  **信号**: 断言中包含大量与被测行为无关的字段；toString() 比较代替精确字段断言。

  ### Anti-Pattern: Conjoined Twins（连体双胞胎）

  名义上的单元测试实际是集成测试——启动了 Spring Context、连接了真实数据库。

  **信号**: 单元测试类使用 @SpringBootTest；测试运行时间 > 5 秒。

  | **全量质量保证** | 同时提供两份文档 | 功能 + 接口 + 单元测试清单 | 正式发布前，全面深入验证 |

  ## 2. 基础层：设计哲学 (Why & Principles)

  ### 2.1 核心挑战：质量陷阱 (The Quality Trap)

  如果不进行系统性的测试设计，软件质量将面临以下风险：

  *   **覆盖盲区 (Blind Spots)**
      *   随意设计测试点，遗漏关键场景（如边界值、异常路径）。
      *   上线后才发现问题，修复成本指数级增加。
  *   **重复低效 (Redundancy & Inefficiency)**
      *   测试用例大量重复，覆盖同类场景，浪费资源。
      *   无法区分优先级，关键路径测试不充分。
  *   **回归噩梦 (Regression Hell)**
      *   缺乏自动化，每次发布需要全量手工回归。
      *   发布周期拉长，质量信心不足。

  ### 2.2 解决之道：逻辑穷举 (Logical Exhaustion)

  > **核心方法论**：追求的不是随意的测试点，而是一份逻辑严密、覆盖正反两面各种情况的**"测试场景清单"**。

  *   **穷举 (Exhaustion)**：针对每个测试维度，系统性地推导出所有可能的场景。
  *   **分层 (Layering)**：不同层次的测试有不同的职责和覆盖目标。
  *   **验真 (Verification)**：参考《业务模拟验证框架》，测试不仅是"跑通流程"，更是对业务逻辑的**验真**。

  ### 2.3 核心原则 (Design Principles)

  1.  **需求可追溯 (Traceability)** — 每个测试用例必须追溯到具体的需求场景或接口规约。
  2.  **场景穷举 (Exhaustive Scenarios)** — 主成功路径 + 所有可能的异常路径 + 边界值。
  3.  **数据守恒 (Data Conservation)** — 业务推演必须满足物理守恒规律。
  4.  **优先级分明 (Clear Priorities)** — Blocker > Critical > Major > Minor。
  5.  **自动化优先 (Automation First)** — 测试清单应设计为可自动化执行。
  6.  **组合最优化 (Combinatorial Optimization)** — 多参数场景采用 Pairwise 算法。
  7.  **副作用隔离 (Side-Effect Isolation)** — 验证"变了什么"，也要验证"没变什么"。
  8.  **故障韧性 (Failure Resilience)** — 将外部依赖故障视为"标准输入"。
  9.  **静态契约验证 (Static Contract Verification)** — 推广领域原语，将运行时测试左移为编译时约束。
  10. **差分与对抗测试 (Differential & Adversarial Testing)** — 引入双盲比对和模糊测试。
  11. **白盒运行时断言 (White-box Runtime Assertion)** — 在代码执行流中植入守恒律探针。

  ## 3. 概念层：核心理论 (What & Concepts)

  ### 3.1 测试金字塔 (Test Pyramid)

  ```
                      +-----------+
                      |   E2E/UI  |  <-- 少量：验证端到端业务流程
                     -+-----------+-
                    / |    API    | \  <-- 中量：验证接口契约与业务规则
                   /  +-----------+  \
                  /   +-----------+   \
                 /    |   Unit    |    \  <-- 大量：验证核心业务逻辑
                ------+-----------+------
  ```

  | 层次 | 速度 | 成本 | 覆盖重点 | 执行频率 |
  | :--- | :--- | :--- | :--- | :--- |
  | **单元测试** | 极快 | 低 | 核心业务逻辑、边界条件 | 每次提交 |
  | **接口测试** | 快 | 中 | 接口契约、业务规则、安全 | 每次构建 |
  | **功能测试** | 慢 | 高 | 端到端用户场景 | 每次发布 |

  ### 3.2 建模维度：T-EBO 测试建模体系

  #### 3.2.1 状态建模 (State-Based) -- 验证"对象稳态"

  聚焦核心业务对象（Entity）的内部一致性：状态转换、业务不变量、竞态条件对抗、MCDC 逻辑覆盖、数据一致性。

  #### 3.2.2 契约建模 (Contract-Based) -- 验证"接口原子性"

  聚焦业务事件（Order）的外部契约：组合最优化、IPO 规则、幂等收敛、对抗性测试、变异思维、原子性。

  #### 3.2.3 链路建模 (Flow-Based) -- 验证"逻辑闭环"

  聚焦业务流程（Process）对多个事件的编排：数据守恒、故障注入与降级、模糊测试、副作用拦截、逻辑连通性、异常补偿。

  ### 3.3 场景推导模式

  #### 3.3.1 功能测试：1+N 模式

  > **"1"** = 主成功路径（Happy Path）
  > **"N"** = 异常与边界路径（四维破坏：输入数据/业务状态/权限/外部依赖）

  #### 3.3.2 接口测试：1+N+M 模式

  > **"1"** = 契约成功场景
  > **"N"** = 参数异常场景（单字段校验）
  > **"M"** = 业务与安全异常场景（跨字段/跨状态规则）

  ### 3.4 单元测试三验证模型

  | 验证维度 | 场景 | 断言方式 | 示例 |
  | :--- | :--- | :--- | :--- |
  | **状态变更** | 对象属性是否发生预期改变 | `assertEquals`, `assertTrue` | `order.getStatus() == "CANCELED"` |
  | **依赖交互** | 是否与 Mock 对象发生正确交互 | `verify()` | `verify(repo, times(1)).save(order)` |
  | **返回值** | 是否返回预期结果或抛出异常 | `assertEquals`, `assertThrows` | `assertThrows(Exception.class, ...)` |

  ## 4. 实践层：标准思维方式 (How & Decisions)

  ### 4.1 测试设计的通用思维范式

  ```
  第一段：定位边界 (Context & Scope) -- 识别职能、依赖与追溯源
  第二段：逻辑推导 (Scenario Deduction) -- 应用 1+N/1+N+M 模式穷举路径
  第三段：验证设计 (Verification Design) -- 定义断言策略、守恒律与副作用
  ```

  ### 4.2 不同层级的执行指令

  | 层级 | 核心关注点 | 引用的建模体系 | 场景推导模式 |
  | :--- | :--- | :--- | :--- |
  | **单元测试** | 隔离依赖、Mock 策略、三验证模型 | 状态建模 | 1+N |
  | **接口测试** | API 契约、Pairwise、对抗性测试 | 契约建模 | 1+N+M |
  | **功能测试** | 业务闭环、四维破坏、数据守恒 | 链路建模 | 1+N |

  ### 5.4 测试设计自检清单

  #### A. 覆盖完整性检查
  - [ ] 主路径覆盖了吗？
  - [ ] 异常路径覆盖了吗？（输入/状态/权限/依赖四维）
  - [ ] 边界值测试了吗？（min-1, min, max, max+1）

  #### B. 可追溯性检查
  - [ ] 每个用例都标注了需求场景ID/接口规约？
  - [ ] 优先级明确了吗？（Blocker/Critical/Major/Minor）

  #### C. TDD 合规检查
  - [ ] 每个测试是否先于实现代码编写？
  - [ ] 是否观察到测试正确失败？
  - [ ] 是否避免了 The Liar / The Mockery / The Inspector 等反模式？

  #### D. 效率检查
  - [ ] 有重复覆盖吗？（单元测试已覆盖的逻辑不需要在 API 测试重复）
  - [ ] 金字塔合理吗？（单元 > 接口 > 功能）

  #### E. 逻辑验真检查
  - [ ] 数据守恒吗？（涉及资产流转的测试，断言了总额守恒吗？）
  - [ ] 逻辑闭环吗？（测试场景是否验证了全生命周期的状态流转？）
