# 不确定性处理

先区分“模式是否合法”和“证据是否充分”。

## 1. 不是不确定性的场景

以下情况若仍能构成正式模式，不应直接视为阻断：

- 缺失需求文档，但存在技术文档 + 代码，可识别为 `DESIGN_CODE`
- 缺失技术文档，但存在需求文档 + 代码，可识别为 `REQ_CODE`
- 缺失代码，但存在需求文档 + 技术文档，可识别为 `REQ_DESIGN`

这些场景属于正式模式，不是异常。

## 2. 何时进入 `BLOCKED`

当出现以下情况时，不能继续正式审查：

- 无法唯一收敛审查对象
- 输入不足以构成任何正式模式
- 模式包含代码，但无法定位实现代码
- 同类实现存在多处，且无法建立真实生效路径的最小判断基础
- 三者都缺失：`PROJECT_ROOT`、`OUTPUT_ROOT`、`OUTPUT_DIR`

## 3. 何时进入 `NEEDS_CONTEXT`

当出现以下情况时，可以继续部分审查，但必须降级：

- 模式已识别，但部分关键来源缺失细节
- 文档只给出摘要，没有足够细节支撑完整判断
- 代码范围只定位到部分实现，仍有未覆盖路径
- 同类实现存在多处，但已能初步定位主要实现，仍有残留不确定分支
- 某些维度缺少足够双边证据

## 4. 何时标记 `UNCERTAIN`

对单条差异结论无法完全确认时，应标记 `UNCERTAIN`，例如：

- 证据只有单边来源
- 文档表述存在歧义
- 代码存在动态路由、配置开关或多态分发，无法确认最终生效路径
- 代码和文档之间存在多个可能映射关系，且无法唯一确认

## 5. 处理要求

- 将不确定项单独放入“需要补充上下文的事项”
- 不确定项不得混入高置信度结论
- 若同一审查对多数结论都处于不确定状态，应在总评中显式降级
- 若第一个审查对已大量不确定，`REQ_DESIGN_CODE` 模式下第二个审查对仍可执行，但必须在链路总评中注明前序基线不稳定
