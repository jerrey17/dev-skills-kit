# release-checklist — 发布CheckList

## 使用场景

dev-workflow 发布CheckList 阶段（bug修复之后、复盘之前）调用。此时代码已是修完 bug 的最终状态，本 skill 生成的 CheckList 是**生产发布的唯一权威操作清单**。

与 `submit-for-testing` 提测文档中"发布 CheckList"章节的分工：提测文档的部署信息**面向测试环境**（给测试同学部署测试环境用）；本产出**面向生产发布**（给发布人按序执行），三块结构。

## 输入参数

| 参数 | 说明 |
|------|------|
| 需求名称 | 用于定位产物目录 |
| 主项目路径 | 确认变更范围 |
| 正式产物目录 | `workflow/{需求名称}/` |

## 执行步骤

### Step 1 — 读取前序产物

读取以下文件：

| 文件 | 提取什么 |
|------|---------|
| `02-服务拆分.md` | 涉及服务列表、部署依赖关系 |
| `03-技术方案.md` | 接口变更、数据库变更、配置变更、灰度方案 |
| `05-代码审查.md` | 遗留问题 |
| `06-单元测试.md` | 测试结果 |
| `07-提测.md` | 服务/接口/配置/依赖/发布顺序（测试环境已验证过一轮的部署信息） |
| `08-bug修复.md` | **关键输入**：bug 清单 + 配置类问题回填清单（修复期新发现的部署注意点、配置项、监控点） |
| `.claude/workflow/{需求名称}/current.md` | 分支名、部署注意、关联项目 |

### Step 2 — 生成「我要操作的」（有序步骤）

这是 CheckList 的第一块，也是**顺序敏感**块。规则：

- 每步一个动作，严格按执行顺序排列
- 每步必须标注：**顺序依赖原因**（为什么必须先做这步）、**验证点**（做完怎么确认成功）、**失败处置**（失败怎么办）
- 顺序错误可能引发生产 bug 的步骤，行首显式标注 **⚠ 顺序敏感**
- 步骤覆盖全链路（按需取舍）：
  1. **DDL / 刷数脚本**（先于服务部署，原因：服务启动依赖表结构/数据就位）
  2. **服务部署**（按依赖顺序：被依赖方先发，逐个服务列分支/commit/部署单元）
  3. **配置开启**（Apollo / OA 审批流 / 运营后台菜单等，标明每个配置项的值和开启时机）
  4. **灰度策略**（feature flag 默认状态、灰度比例、灰度范围）
  5. **上线验证**（生产冒烟：验证哪个接口/页面/任务，预期结果）
- 一仓多部署单元（如 atm_api + atm_task 共享模块）必须全部列出，标注"无先后要求但都必须部署"

### Step 3 — 生成「我要关注的」

第二块，发布后观察期需要盯的内容：

- **监控指标**：报警项 + 正常基线（如"接口错误率基线 <1%，>5% 持续 10 分钟触发回退评估"）
- **业务观察点**：功能使用量、任务成功率、上下游服务负载（新链路对上游的放大效应）
- **遗留风险**：所有未完全解决的问题，逐项列出（描述/影响级别/处理方式/跟进人），**等待用户逐项确认接受**后才写入
- **bug 修复回填关注项**：`08-bug修复.md` 回填清单中标记为"发布后关注"的项（如配置一致性核查、脏数据核查 SQL 上线后执行）

### Step 4 — 生成「如何回退」

第三块，独立成块、可单独执行：

- **回退触发条件**：可量化（错误率/耗时/业务指标阈值 + 持续时间）
- **回退步骤**：也有顺序（先关 flag / 先回滚哪个服务 / 配置如何复位），每步标注生效时间和影响
- **回退影响范围**：数据是否可逆、在途任务/用户影响、老功能是否完全无感

### Step 5 — 人工确认

将三块内容展示给用户，重点确认：
1. 「我要操作的」步骤顺序是否正确、依赖原因是否成立
2. 遗留风险逐项是否接受
3. 回退触发条件和步骤是否可执行

**用户确认后才写入产出文件。**

### Step 6 — 写入产出文件

写入 `workflow/{需求名称}/09-发布CheckList.md`：

```markdown
# 09-发布CheckList — {需求标题}

- 生成时间 / 分支 / 涉及服务 / 发布结论依据（bug 修复闭环状态）

## 一、我要操作的（按顺序执行，顺序错误可能引发生产 bug）

| # | 动作 | 顺序依赖原因 | 验证点 | 失败处置 |
|---|------|------------|--------|---------|
| 1 | ... | ... | ... | ... |

## 二、我要关注的

### 监控指标
### 业务观察点
### 遗留风险（已逐项确认）
| # | 风险描述 | 影响级别 | 处理方式 | 确认人 |

## 三、如何回退

### 回退触发条件
### 回退步骤（按序）
### 回退影响范围

## 四、发布结论

{可以发布 / 可以发布（附条件）/ 需修复后发布 / 阻塞发布} + 条件说明

## 小结

- 产出: {文件清单}
- 阻塞: {无，或简述}
- 已知缺口: {无，或简述}
- 交接: {一句话，复盘阶段必须知道的}
```

文件末尾追加 `## 小结` 段落，4 个固定 bullet（独立调用时也写，非 dev-workflow 专属）。

## 产出文件

`workflow/{需求名称}/09-发布CheckList.md`
