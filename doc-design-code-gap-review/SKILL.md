# 文档与代码差异审查

## 概览

该 skill 用于对以下三类输入做证据约束型差异审查：

- 需求文档
- 技术文档
- 代码实现

其中“技术文档”包括但不限于：

- 技术方案
- 设计文档
- 概要设计
- 详细设计

本 skill 不做泛化 review，而是先识别审查模式，再按固定审查对输出一份基于证据、可追溯、低幻觉的《差异审查报告》。

## 正式审查模式

读取 `references/审查模式规则.md`，识别本次任务属于以下哪一种正式模式：

1. `REQ_DESIGN`
   - 输入组合：需求文档 + 技术文档
   - 审查对：需求 -> 技术文档

2. `DESIGN_CODE`
   - 输入组合：技术文档 + 代码
   - 审查对：技术文档 -> 代码

3. `REQ_CODE`
   - 输入组合：需求文档 + 代码
   - 审查对：需求 -> 代码

4. `REQ_DESIGN_CODE`
   - 输入组合：需求文档 + 技术文档 + 代码
   - 审查对：
     - 需求 -> 技术文档
     - 技术文档 -> 代码

说明：

- `REQ_DESIGN_CODE` 仍然按两段顺序执行，不做三方平级混合对比
- “缺少某一类输入”只有在无法构成任何正式模式时，才视为上下文不足

## 输入要求

- 至少提供以下信息中的大部分：
  - 项目根目录
  - 输出根目录或输出目录（可选）
  - 需求文档路径或内容
  - 技术文档路径或内容
  - 接口名、模块名、类名、方法名、需求编号中的至少一项
- 代码参与审查时，还应尽量提供：
  - 代码根目录
  - 可疑接口路径、类名、方法名、DTO 名称、错误码关键字中的至少一项

执行前必须先识别模式：

- 若输入可构成 4 种正式模式之一，则进入正式审查
- 若模式已成立，但证据不足、范围未收敛或代码无法定位，可继续部分审查并标记 `NEEDS_CONTEXT`
- 若既无法构成正式模式，也无法收敛对象，则标记 `BLOCKED`

## 铁律

1. **先识别模式并收敛范围，后做审查**：若无法明确本次审查的接口、模块、类、方法或需求，不得进入正式差异审查。
2. **先生成中间产物，后输出结论**：未生成《来源清单》与所需《对齐矩阵》前，不得输出正式《差异审查报告》。
3. **每条问题必须带证据**：每条差异必须附文件路径与章节位置或行号；没有证据的结论一律标记 `UNCERTAIN`。
4. **代码事实优先**：文档与代码不一致时，以代码为事实基线，但必须显式标注文档与代码的差异。
5. **禁止自由发挥式总结**：不得把需求、技术文档、代码原文一次性塞入同一轮上下文后直接总结。
6. **按审查对执行**：必须先确定本次有哪些审查对，再逐一完成对应对齐矩阵；仅 `REQ_DESIGN_CODE` 模式要求按两段顺序执行。
7. **不修改业务内容**：不修改业务代码、测试代码、需求文档、技术文档。

## Step 0：识别审查模式并收敛范围

读取输入、项目上下文与 `references/审查模式规则.md`，明确本次审查对象：

- 审查模式
- 审查任务
- 审查对象
- 纳入范围
- 排除范围
- 可执行的审查对列表

审查对象至少要收敛到以下项中的若干个：

- 接口
- 模块
- 目标类 / 方法
- 需求编号

输出《审查范围》：

- 审查模式
- 审查任务
- 审查对象
- 纳入范围
- 排除范围
- 审查对列表

阻断条件：

- 无法回答“本次到底审查哪个接口/模块/需求”
- 输入不足以构成任何正式模式
- 找不到文档与代码的基本对应关系

完成后勾选：`- [x] Step 0：识别审查模式并收敛范围`

## Step 1：生成《来源清单》

读取 `assets/来源清单模板.md`，按当前模式建立来源清单。

来源类型最多包含三类：

1. 需求文档
2. 技术文档
3. 代码文件

要求：

- 每个来源都必须记录纳入原因和关注维度
- 没有纳入原因的文件不得作为正式证据
- 没进入《来源清单》的文件，不应直接进入结论段落
- 仅统计当前模式实际使用的来源类型

输出文件：`《来源清单》`

完成后勾选：`- [x] Step 1：生成《来源清单》`

## Step 2：生成所需事实清单

读取 `assets/事实卡片模板.md`，只针对当前模式实际使用的输入抽取原子事实。

按输入类型生成：

- 有需求文档：生成 `《需求事实清单》`
- 有技术文档：生成 `《技术事实清单》`
- 有代码实现：先读取 `references/代码定位策略.md` 收敛代码范围，再生成 `《代码事实清单》`

重点维度读取 `references/审查维度规则.md`，至少覆盖：

- 接口契约
- 参数校验
- 状态流转
- 异常处理
- 错误码
- 数据落库 / 表结构影响
- 配置项
- 外部依赖调用
- 兼容性要求

要求：

- 一张事实卡片只表达一个原子事实
- 每条事实必须绑定章节或位置
- 不做结论，只做事实抽取
- 不为未纳入当前模式的来源类型生成空白事实清单

完成后勾选：`- [x] Step 2：生成所需事实清单`

## Step 3：生成所需对齐矩阵

读取 `references/审查模式规则.md`、`references/审查维度规则.md` 与 `assets/对齐矩阵模板.md`，按审查对生成对齐矩阵。

矩阵生成规则：

- `REQ_DESIGN`：生成 `《需求-技术对齐矩阵》`
- `DESIGN_CODE`：生成 `《技术-代码对齐矩阵》`
- `REQ_CODE`：生成 `《需求-代码对齐矩阵》`
- `REQ_DESIGN_CODE`：生成：
  - `《需求-技术对齐矩阵》`
  - `《技术-代码对齐矩阵》`

要求：

- 一行只表达一个明确对齐点或差异点
- 必须明确：
  - 对象
  - 基线层
  - 基线事实
  - 对齐层
  - 对齐事实
  - 差异落点
  - 差异点
  - 对齐结论
  - 差异类型
- 对“代码有实现但基线层无定义”的场景，显式标记为 `CODE_EXTRA`

完成后勾选：`- [x] Step 3：生成所需对齐矩阵`

## Step 4：生成《差异审查报告》

读取 `references/证据规则.md`、`references/不确定性处理.md` 与 `assets/差异审查报告模板.md`，基于当前模式生成正式报告。

要求：

- 每条差异必须带证据
- 明确“差异发生在哪里”和“差异点是什么”
- 缺少证据或上下文时，标记 `UNCERTAIN` 或 `NEEDS_CONTEXT`
- 报告章节必须与当前模式匹配，不保留无意义空章节

单审查对模式至少区分：

- 基线未被对齐层承接
- 基线与对齐层不一致
- 代码超出基线定义（仅当对齐层为代码）
- 局部对齐但存在遗漏

`REQ_DESIGN_CODE` 模式还需补充：

- 需求 -> 技术文档总体对齐情况
- 技术文档 -> 代码总体对齐情况
- 是否存在链路断点
- 是否存在代码额外实现

输出文件：`《差异审查报告》`

完成后勾选：`- [x] Step 4：生成《差异审查报告》`

## 落盘规范

- 支持以下三个路径变量：
  - `PROJECT_ROOT`：项目代码根目录
  - `OUTPUT_ROOT`：用户指定的输出根目录，可选
  - `OUTPUT_DIR`：用户指定的完整输出目录，可选，优先级最高
- 路径优先级：
  1. 若用户显式提供 `OUTPUT_DIR`，则直接写入该目录
  2. 若用户显式提供 `OUTPUT_ROOT`，则写入 `OUTPUT_ROOT/.ai_work_space/<YYYY-MM-DD>/doc-design-code-gap-review/`
  3. 若用户未指定输出路径，则默认写入 `PROJECT_ROOT/.ai_work_space/<YYYY-MM-DD>/doc-design-code-gap-review/`
- 若 `PROJECT_ROOT` 缺失但用户已提供 `OUTPUT_DIR` 或 `OUTPUT_ROOT`，允许继续执行并按用户指定路径落盘
- 若三者都缺失，则阻断并要求用户补充项目根目录或输出路径

建议文件名：

- `审查范围.md`
- `来源清单.md`
- `需求事实清单.md`
- `技术事实清单.md`
- `代码事实清单.md`
- `需求-技术对齐矩阵.md`
- `技术-代码对齐矩阵.md`
- `需求-代码对齐矩阵.md`
- `差异审查报告.md`

按模式只生成需要的文件，不生成空文件。

## 完成状态

- `DONE`：模式已成立，证据充分，审查完成，报告可直接使用
- `DONE_WITH_CONCERNS`：模式已成立，审查完成，但存在明显差异或中高风险
- `NEEDS_CONTEXT`：模式已成立，但缺少部分证据、代码范围或文档细节，只能输出部分结论
- `BLOCKED`：无法构成正式模式，或范围无法收敛，不能继续
