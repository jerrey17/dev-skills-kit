# req-analysis — 需求分析

## 目标

把需求整理成一个可直接进入后续服务拆分和技术方案阶段的分析文档。

这个 skill 只做三件事：
1. 保留并整理原始需求和附件
2. 基于需求相关知识子图做审查
3. 输出 `01-需求分析.md`

这个 skill **不负责**：
- 更新 `current.md`
- 决定是否进入下一阶段
- 执行服务拆分或技术方案设计

这些由 `dev-workflow` 负责。

---

## 执行模式

### 模式 A：dev-workflow 调用

输出目录固定为：

```text
{项目根目录}/workflow/{需求名称}/
```

产出：
- `01-需求分析.md`
- `attachments/`

### 模式 B：独立使用

输出目录固定为：

```text
{当前工作目录}/需求分析文档/{需求名称}/
```

产出：
- `01-需求分析.md`
- `attachments/`

如果用户明确指定目录，按用户指定目录执行。

---

## 流程概览

```text
Step 1 采集需求内容与附件元信息
Step 2 确定输出目录并创建文档骨架
Step 3 提取需求锚点
Step 4 GraphRAG 定向加载知识子图
Step 5 下载附件并写入附件引用
Step 6 四轮审查
Step 7 生成最终文档与返回摘要
```

---

## Step 1 — 采集需求内容与附件元信息

### 输入来源

**方式 A：TAPD 链接或 ID**

从链接提取 `workspace_id` 和需求 ID，调用 `mcp__tapd__get_stories_or_tasks` 拉取需求详情。

优先获取这些信息：
- 标题
- 原始描述
- 创建人
- 处理人
- 需求分类
- 状态
- 迭代信息

同时调用 `mcp__tapd__get_entity_attachments` 获取附件列表。

如果只拿到 `iteration_id` 而没有迭代名称：
- 能补查就补查
- 不能补查就先写 `iteration_id`
- 不要因为迭代名称缺失阻断流程

**方式 B：用户直接提供**

直接使用用户提供的标题、描述、附件路径或附件说明。

### 原始内容保留原则

原始需求内容必须完整保留，不得删减、改写、归纳替代。

文档结构上分成两块：
- `原始需求内容`：只放原文
- `审查结论`：只放分析和建议

不要把 AI 的解释混进原始需求区域。

---

## Step 2 — 确定输出目录并创建文档骨架

先确定执行模式，再创建目录。不要在目录创建前处理附件。

目录结构：

```text
{输出目录}/
├── 01-需求分析.md
└── attachments/
```

`01-需求分析.md` 初始结构：

```markdown
# 需求分析：{需求标题}

## 基本信息
| 字段 | 内容 |
|------|------|
| 需求标题 | {标题} |
| TAPD ID | {ID 或 N/A} |
| 创建人 | {创建人} |
| 处理人 | {处理人} |
| 迭代 | {迭代名称或 ID 或 N/A} |
| 需求分类 | {分类或 N/A} |
| 分析日期 | {当前日期} |

## 原始需求内容

{原始需求描述，完整保留，不修改}

## 附件清单

（待填充）

## 审查结论

> 以下内容为 AI 审查结果，不修改原始需求，仅用于识别开发前风险和待确认问题。

### 总体结果

| 维度 | 结果 | 说明 |
|------|------|------|
| 完整性 | - | - |
| 合理性 | - | - |
| 数据充分性 | - | - |
| 扩展建议 | - | - |

### Pass 1 — 完整性审查
### Pass 2 — 合理性审查
### Pass 3 — 数据充分性审查
### Pass 4 — 需求扩展项

## 审查摘要

（待填充）
```

## Step 3 — 提取需求锚点

先从需求标题和描述里提取锚点，再决定检索范围。

提取三类锚点：

1. **业务对象**
   - 用户、账户、订单、银行卡、代扣协议、还款计划、资金流水等
2. **业务动作**
   - 绑卡、扣款、还款、退款、重试、查询、同步、回调等
3. **服务候选**
   - 用户服务、收银台、交易订单中心、代扣服务、消息通知等

### 锚点优先级

不要把所有词都送去检索。先做一次轻量排序：

- 第一优先级：标题里的对象和动作
- 第二优先级：描述中反复出现的对象和动作
- 第三优先级：从对象和动作推断出的服务候选

只保留最关键的 2-4 个锚点用于下一步检索。

---

## Step 4 — GraphRAG 定向加载知识子图

这里的目标不是"搜更多文档"，而是拿到**足够支撑审查的需求相关子图**。

### 知识来源优先级

在这个 skill 里，证据优先级固定如下：

1. **原始需求内容**
2. **附件原件**
3. **知识库检索结果**
4. **模型基于上下文的推断**

知识库信息默认只是**旁证**，不能覆盖原始需求和附件里的直接信息。

如果知识库信息与需求原文或附件冲突：
- 不要擅自裁定哪一方正确
- 在审查结论中明确标注 `需人工确认`
- 写清楚冲突点分别来自哪里

### 检索工具顺序

优先用 GitNexus 代码知识图谱做定向检索：
- 第一优先级：`mcp__gitnexus__query`（语义搜索执行流和代码符号）
- 第二优先级：`mcp__gitnexus__context`（获取特定符号的 360 度视图）
- 第三优先级：`mcp__gitnexus__cypher`（精确的图数据库查询）

如果 GitNexus 无结果或结果不足：
- 不要阻断流程
- 继续基于原始需求和附件完成审查
- 在结论里标注"知识库旁证不足"

### 检索顺序

按下面顺序检索，命中足够信息就停止：

1. **服务边界**
   - `"{服务候选} 服务边界 接口"`
2. **业务流程 / 规则**
   - `"{业务对象} {业务动作} 业务规则 流程"`
3. **数据模型**
   - `"{业务对象} 数据模型 字段"`
4. **一跳依赖**
   - 如果前面结果明确提到上下游依赖，再补查 `"{依赖服务} 接口规范"`

### 停止条件

满足以下 3 项中的 2 项即可停止，不必凑满检索次数：
- 已基本确认服务归属
- 已拿到核心业务规则或流程约束
- 已拿到主要数据模型或字段线索

### 检索上限

最多 5 次。需求简单时 2-3 次即可。

### 内部整理结果

把检索结果整理成 4 类证据，供后续审查使用：
- **服务归属证据**
- **业务规则证据**
- **接口证据**
- **数据模型证据**

如果知识库没有结果，明确写：
- 知识库暂无直接命中
- 后续审查更多依赖需求原文本身

不要因为知识库缺失而中断分析。

对用户只输出一句简短摘要，例如：
> 已加载需求相关知识子图，已确认主要服务边界和部分业务规则，开始审查。

## Step 5 — 下载附件并写入附件引用

附件核心原则：**下载到目录内，在文档里引用文件；图表类附件额外内嵌到文档中**。

### 附件分类处理

#### 普通附件（文档、表格、数据文件）

1. 把 TAPD 附件下载到 `{输出目录}/attachments/`
2. 用户直接给的本地文件：放到 `attachments/` 目录内
3. 下载失败或无权限时：在附件清单中记录附件名，标注 `未成功下载` 或 `需用户补充`

在 `附件清单` 中用链接引用，格式：

```markdown
- [字段样例.xlsx](./attachments/字段样例.xlsx)
- 风控规则.docx（未成功下载，需用户补充）
```

#### 图表类附件（流程图、原型图、交互图）

图表类附件除了加入附件清单外，还必须**内嵌到文档**中。判断依据：
- 文件名或描述包含"流程图"、"原型"、"交互"、"UI"、"设计稿"、"mockup"、"prototype"、"wireframe"
- 文件扩展名为 `.png`、`.jpg`、`.jpeg`、`.gif`、`.svg`、`.pdf`（且标题暗示视觉内容）

**处理规则：**
1. 下载到 `{输出目录}/attachments/`
2. 在附件清单中链接引用（同普通附件）
3. 额外在文档中创建 `## 需求图表` 章节，用 `![]()` 语法内嵌图片

```markdown
## 需求图表

### {图表名称}

![{图表名称}](./attachments/{文件名})

> 来源：{附件名称 / TAPD 附件 / 用户提供}
```

4. 如果附件下载失败，在 `需求图表` 章节保留占位：

```markdown
### {图表名称}

（图表未能下载，请补充 `attachments/{文件名}`）
```

#### 需求描述中内嵌的图表

有时需求描述原文中包含图表 URL（图床链接、TAPD 内嵌图片等）：

1. 识别需求描述里的图片 URL（`http://` 或 `https://` 开头，后缀为图片格式）
2. 尝试下载到 `{输出目录}/attachments/`，文件名用 URL 末段或 `inline-图-{序号}.png`
3. 下载成功 → 替换为本地相对路径，并在 `需求图表` 章节内嵌
4. 下载失败 → 在 `需求图表` 章节保留原始 URL 链接，标注 `（在线图，建议手动保存）`

不要把附件确认设为固定阻塞节点。默认直接下载和引用即可。

## Step 6 — 四轮审查

结合需求原文、附件引用和 Step 4 的知识子图证据进行审查。

### Pass 1 — 完整性审查（0-10）

目标：找出需求中缺失的必要信息，也就是会让开发阶段卡住的问题。

重点检查：
- 核心流程是否完整
- 前置条件是否明确
- 边界条件是否明确
- 异常处理是否明确
- 角色 / 权限是否明确
- 外部依赖是否明确

输出结构：

```markdown
### Pass 1 — 完整性审查

**评分：{X}/10**

**待确认问题：**
1. **[问题类型]** {问题描述}
   - 影响：{影响说明}
   - 建议：{建议补充内容}

**已明确部分：**
- {已覆盖点}
```

### Pass 2 — 合理性审查（0-10）

目标：判断这套需求是否在业务逻辑、用户体验、技术约束上说得通。

重点检查：
- 是否与已有业务规则冲突
- 用户流程是否顺畅
- 是否超出现有服务能力
- 是否存在支付安全或合规风险
- 是否会引入明显性能问题

输出结构：

```markdown
### Pass 2 — 合理性审查

**评分：{X}/10**

**主要问题：**
1. **[问题类型]** {问题描述}
   - 风险：{风险说明}
   - 建议：{建议方案}

**合理设计：**
- {合理点}
```

### Pass 3 — 数据充分性审查（0-10）

目标：识别字段、来源、存储、流向上的缺失。

重点检查：
- 字段是否列清楚
- 字段来源是否明确
- 数据落库或缓存方案是否明确
- 服务间流转是否明确
- 历史数据处理是否明确
- 一致性要求是否明确

输出结构：

```markdown
### Pass 3 — 数据充分性审查

**评分：{X}/10**

**主要问题：**
1. **[数据问题类型]** {问题描述}
   - 影响：{影响说明}
   - 建议：{建议补充内容}

**已明确数据点：**
- {明确点}
```

### Pass 4 — 需求扩展项

目标：提出值得评估、但不一定要纳入本期的补充项。

常见维度：
- 监控与告警
- 降级与回滚
- 运营后台能力
- 用户通知触达
- 权限管控
- 报表与统计

输出结构：

```markdown
### Pass 4 — 需求扩展项

| 扩展项 | 建议原因 | 优先级 |
|--------|---------|--------|
| {扩展项} | {原因} | 高/中/低 |
```

---

## Step 7 — 生成最终文档与返回摘要

### 回填总体结果

```markdown
### 总体结果

| 维度 | 结果 | 说明 |
|------|------|------|
| 完整性 | {分数}/10 | {一句话总结} |
| 合理性 | {分数}/10 | {一句话总结} |
| 数据充分性 | {分数}/10 | {一句话总结} |
| 扩展建议 | {条数} 条 | {一句话总结} |
```

### 生成审查摘要

```markdown
## 审查摘要

**综合结论**：{一句话结论}

**开发前必须确认（阻塞项）**：
1. {问题描述} — 影响：{影响说明}

**建议优化但不阻塞（非阻塞项）**：
1. {问题描述}

**可并行评估的扩展项**：
- {扩展项}
```

### 产出文件末尾的「小结」段落（必写）

在 `01-需求分析.md` 末尾追加 `## 小结` 段落，3 个固定 bullet。独立运行时也写（作为阶段文档小结，非 dev-workflow 专属）：

```markdown
## 小结

- 产出: {文件清单，逗号分隔，如 workflow/XX/01-需求分析.md}
- 阻塞: {无，或简述阻塞项；如"需产品确认短信发送频次"}
- 交接: {一句话，下一阶段必须知道的；如"需求范围已圈定，服务拆分可基于此设计"}
```

**字段规则**：
- `产出`：本阶段产出的所有文件路径
- `阻塞`：开发前必须解决的阻塞项；无则写"无"
- `交接`：下一阶段必须知道的关键信息（一句话），不重复正文摘要

### 面向用户的结束语

结束时只说明分析结果，不负责推进流程：
> 需求分析完成，文档已保存到 {路径}。当前有 {M} 个阻塞项需要先确认。

---

## 与 dev-workflow 的集成

- `req-analysis` 负责生成 `01-需求分析.md`
- `dev-workflow` 负责更新 `current.md`
- `dev-workflow` 负责决定是否进入服务拆分阶段

如果由 `dev-workflow` 调用，优先遵循它传入的目录和需求名称。
