# 技术方案设计（按模板生成）

> 文档版本：2.6.0

## 定位

把**需求文档**转成 0~8 章齐全、可贴到 TAPD/Wiki 评审的**技术方案初稿**。

## 适用输入

- `02-服务拆分.md`（service-split 产出，优先级最高的结构化输入；含全局业务流程、服务边界、改动清单）
- PRD / 用户故事 / 需求说明 / 对话整理稿
- 已有技术方案草稿（评审补全 / 优化模式）
- 允许输入不完整：缺失信息标记 `TBD`，汇入文末"待澄清清单"
- TAPD 需求链接（如 `https://www.tapd.cn/{workspace}/prong/stories/view/{id}`），自动通过 `scripts/call_tapd_mcp.py fetch --url <link>` 拉取需求内容后进入设计流程

### 知识库（唯一规范来源）

知识库根目录与索引文件由 `scripts/kb.config.json` 配置（字段：`access_mode` / `kb_root` / `kb_index_file` / `include_globs` / `exclude_globs` / `mcp_remote`）。**路径不写死在 SKILL.md 中，所有引用均从配置文件读取。**

**访问方式（按 access_mode）**：

- `access_mode: "local"`（默认，主路径）：直接 Read `kb_root` 下的 Markdown 文件；关键词检索用 `scripts/call_kb.py search -k <keyword>`（底层 ripgrep 或 grep），列目录用 `list`，打印索引用 `index`。skill 允许对 `kb_root` 目录下的 `.md` 文件使用 Read 工具。
- `access_mode: "remote_mcp"`（可选降级）：通过 `scripts/call_kb.py` 调用 MCP Streamable HTTP 端点（`mcp_remote` 字段配置 `url`/`headers`/`timeout`），映射到 `rag_doc_search` / `rag_doc_read` / `rag_doc_list`。

**子命令**：`search -k <keyword> [--path-must-contain <dir>]` | `read -f <filePath>` | `list [--path <dir>] [--recursive]` | `index`（仅 local） | `tools`（仅 remote_mcp）

**环境准备**：将 `scripts/kb.config.example.json` 复制为 `scripts/kb.config.json`，填入 `kb_root`（本地知识库根目录绝对路径）和 `kb_index_file`（默认 `_INDEX.md`）。`access_mode=remote_mcp` 时额外安装 `python3 -m pip install -U -r scripts/requirements-mcp.txt`。

**知识库不可用时**：`access_mode=local` 且 `kb_root` 不存在或 `kb_index_file` 缺失 → **立即终止方案生成**，告知用户修复 `kb.config.json` 后重新发起。方案必须依赖知识库规范，**不得**在无法访问知识库的情况下继续生成，**不得**凭记忆或非配置来源替代。

**调用纪律**：**仅当**工作流确实需要知识库时执行（Step 0c 探测、Ch 3 选型、Ch 4 系统边界、Ch 5 数据库设计、6.x.3/6.x.5 接口设计、Step 4 自检等）。**不得**依赖固定文件名或章节号定位条文——知识库结构可能变化，以 `kb_index_file` 解析结果为准。

### TAPD 需求拉取（按需）

**统一通过 `scripts/call_tapd_mcp.py`**（stdio 模式，启动 `uvx mcp-server-tapd` 子进程）拉取 TAPD 需求/缺陷等内容。

**子命令**：`fetch --url <tapd_link>` | `tools` | `call <tool_name> --args '{...}'`

**环境准备**：将 `tapd_mcp.config.json` 中 `TAPD_ACCESS_TOKEN` 填入实际值。依赖同 `requirements-mcp.txt`。

**脚本不可用时**：**不终止**方案生成（与知识库不同），提示用户手动粘贴需求内容后继续。

**调用纪律**：**仅当**用户输入为 TAPD 链接时在 Step 0.5 执行，后续流程不再重复调用。

### GitNexus 项目代码探测（条件触发）

**触发条件**：需求明确涉及对某个已有项目的**二次开发 / 功能扩展 / 技术改造**（用户指定了目标项目，或从需求内容可判断目标代码仓库）。特别地，当需求涉及具体 API 路径时，该路径可能跨越多个微服务（如入口网关 + 业务服务），需要跨项目追踪完整调用链。

**目的**：通过 GitNexus MCP tools 了解目标项目的现有架构、相关执行流程、接口设计，作为方案设计的**优先参考**（项目实际代码 > 知识库通用规范）。

**可用工具**（均为编辑器内置 MCP tool，直接调用，无需脚本）：

| 工具 | 用途 | 典型场景 |
|------|------|---------|
| `mcp__gitnexus__list_repos` | 列出已索引项目 | Step 0.5 确认目标项目可探测 |
| `mcp__gitnexus__query` | 按关键词搜索执行流程（process） | 查找与需求相关的现有业务流程、调用链 |
| `mcp__gitnexus__context` | 符号 360 度视图（调用者/被调用者/所属模块） | 深入了解核心类/方法的上下游依赖 |
| `mcp__gitnexus__impact` | 变更影响分析（blast radius） | 评估改造/扩展对现有代码的影响范围 |
| `mcp__gitnexus__route_map` | API 路由映射（handler + consumer） | 查看现有接口及其调用关系 |
| `mcp__gitnexus__cypher` | Cypher 查询知识图谱 | 复杂结构查询（如查找所有继承某基类的实现） |

**调用纪律**：
- **仅在 Step 0.5 集中探测**，后续设计阶段通过 `.project-context.md` 工作文件引用，不重复调用
- 探测范围聚焦需求相关模块，**不全量扫描**项目
- 所有工具调用须指定 `repo` 参数（项目名，从 `list_repos` 获取）
- **跨项目接口追踪（强制）**：当需求涉及具体 API 路径时，**必须**在所有已索引项目中执行 `route_map` 或 `query` 确认该路径的完整请求链路（从 API 入口到最终执行），将链路上的所有项目纳入探测范围。**不得**仅探测用户指定的单个项目后即认为探测完成

**与知识库的优先级**：
- **项目代码探测结果 > 知识库通用规范**：项目已有的命名规范、分层结构、接口风格、设计模式优先遵循
- **知识库规范仍为兜底**：项目代码中未体现的规范（如通用建表规范、接口规范总则）仍从知识库拉取
- **冲突处理**：以项目现有实践为准，在方案中标注「与知识库规范 {xxx} 存在差异：{描述}，遵循项目现有实践」

## 知识库检索流程（共 5 个，按需触发）

所有流程共享原则：`Read .kb-map.md` 确定目标文件 → **优先 `search`**（可多次、可换词）→ 片段不足时 `read -f` 辅助核对。`path-must-contain`：根据 `.kb-map.md` 中目标文件实际路径决定（如 `contract/数据结构`、`sms/交接内容`、`base_specifications` 等），不固定为单一目录。

**⚠️ `read -f` 使用限制**：由于工具输出存在上下文窗口截断（约 200 行），`read -f` 获取的内容**可能不完整**。使用规则如下：

| 场景 | 推荐方式 | 原因 |
|------|---------|------|
| 获取某个具体规范条文/字段/接口定义 | `search -k` | 精准定位，不受截断影响 |
| 确认文档整体结构/目录 | `read -f`（仅看前 200 行目录区） | 大部分文档目录在开头 |
| 获取文档后半部分内容 | `search -k`（用该段落的关键词） | read 会被截断，后半部分不可见 |
| 同一文档需要多个段落 | 多次 `search -k`（不同关键词） | 每次 search 返回匹配片段，不受位置限制 |

**严禁**：仅通过一次 `read -f` 就认为已获取文档全部内容。当需要的信息可能位于文档后半部分时，**必须用 search 交叉验证**。

### 1. 业务域与接口检索

**触发**：涉及已有业务系统交互、接口复用/扩展、上下游调用时（Ch 1/3/4、6.x.3、6.x.5）

**关键词**：`{业务域名}`、`{系统名}`、`接口清单`、`对外接口`、`API`、`上游`、`下游`、`回调`、`能力`、`已有`

**对齐范围**：
- **系统边界**（Ch 4）：与知识库业务域划分一致，避免职责越界
- **接口复用**（6.x.3）：已有接口**必须复用**并标注来源；不存在的标注「新增接口」
- **接口设计**（6.x.5）：新增接口不得与已有接口功能重叠（有重叠须说明差异和理由）
- **数据流/业务流程**：字段命名与已有接口一致；新增环节标注插入点

### 2. 接口规范检索

**触发**：写 6.x.5 对外契约、Ch 8 保障时

**关键词表**：

| 场景 | 关键词 |
|------|--------|
| 接口总则 | `接口规范`、`接口设计原则`、`API 规范` |
| REST（默认） | `RESTful`、`REST`、`统一响应`、`code message data`、`URL` |
| PB（仅用户要求时） | `PB`、`Protobuf`、`RequestBasic`、`ResponseBasic`、`proto` |

**步骤**：① 先完成「术语检索」→ ② 接口总则关键词建立上下文 → ③ 默认 REST 行检索（用户要求 PB 时用 PB 行，**同一功能点只用一种协议**）

> **响应结构约束**：接口响应消息中，错误信息（错误码、错误描述等）的承载方式须以知识库中检索到的**公共响应基类**（如 REST 统一响应体 / PB ResponseBasic 等）为准。Response 消息中**不得**新增已由公共响应基类承载的字段。检索到公共响应基类结构后，须以此为准设计 Response 消息体。
>
> **PB 接口特别约束**：`ResponseBasic` 已包含 `code`（int, 状态码）、`msg`（string, 错误描述）、`scode`（string, 业务错误码）、`time`（long, 时间戳）。PB Response message 中**仅定义业务数据字段**，**不得**新增 code/msg/scode/error_code/error_msg 等错误码相关字段。错误码表中的 code/msg 对应的是 `ResponseBasic.scode` / `ResponseBasic.msg` 的取值，不是 Response message 的独立字段。

### 3. 术语与命名规范检索

**触发**：凡出现接口字段名、DB 列名、表名业务词、MQ 消息体字段名时，**必须先**按本流程检索再落笔

**关键词**：`术语`、`命名`、`字段命名`、`词表`、`业务词`、`缩写`、`接口 命名`、`数据库 命名`

**【强制】术语词表缓存**：首次触发时（通常子段落 1 写 Ch 5 前；Ch 5 不涉及表则推迟到子段落 2 写 6.x.5 前），将业务词表写入 `{工作流目录}/.terminology-cache.md`：

| 业务概念 | 接口字段名(camelCase) | DB列名(snake_case) | 缩写规则 | 来源文件 |
|---------|---------------------|-------------------|---------|---------|

后续子段落动笔前 `Read .terminology-cache.md` 加载。新增业务词时先 `search` → **更新文件** → 再使用。

**对齐范围**：接口字段/URL 资源名/错误码用词 + DB 表列业务词/缩写 + MQ 消息体字段名。检索词条优先于口语化拼写。

### 4. MySQL 建表规范检索

**触发**：新建/变更表、索引、DDL 时（Ch 5、6.x.7）

**关键词**：`建表`、`表命名`、`字段类型`、`索引`、`DDL`、`InnoDB`、`utf8mb4`、`支付`、`金额`、`bigint`、`NOT NULL`、`默认值`

**对齐范围**：
- **表级**：命名前缀、引擎/字符集、分库分表
- **字段级**：类型、NOT NULL、默认值、必备字段（列名业务词与**术语检索**一致）
- **索引级**：命名规则（`idx_`/`uniq_`）、数量上限、唯一约束
- **DDL 书写**：注释、脚本组织。`references/examples/` 仅提供形态示例，合规性以规范条文为准
- **支付/资金**：补充 `支付`、`资金`、`状态机` 关键词检索

### 5. 公共组件与外部依赖检索

**触发**：方案涉及通用能力（如分布式锁、MQ、缓存、流程编排、幂等框架、加解密、签名验签、渠道路由等）或外部系统对接（渠道、财务系统、风控等）时（Ch 3/4、6.x.3、6.x.5、Ch 8）

**检索路径**：以 `kb_index_file`（如 `_INDEX.md`）为入口，查看其中「工具与内部组件」分类是否有对应组件的说明文档 → 有则 `read -f` 获取组件说明，**重点关注组件接口的出入参字段定义**（字段名、字段类型、必填/选填、字段含义）

**关键词**（`kb_index_file` 中未直接列出时用于补充搜索）：`公共组件`、`中间件`、`框架`、`SDK`、`工具类`、`外部依赖`、`三方`、`渠道`、`{具体组件名}`

**对齐范围**：
- **选型决策**（Ch 3）：已有公共组件能满足需求时**必须复用**，不得重复建设
- **系统边界**（Ch 4）：外部依赖须纳入涉及系统，标注交互方式与职责
- **接口设计**（6.x.5）：`kb_index_file`「工具与内部组件」中有对应组件说明的，**接口出入参字段必须按组件说明文档设计**（字段名、字段类型、结构与组件约定保持一致）；无说明文档的按通用接口规范设计，并标注「该组件无知识库说明文档」
- **上线保障**（Ch 8）：外部依赖须列明超时/重试/熔断/降级策略

> **上下文管理**：按需分段加载，每个子段落仅加载该步所需规范片段，Step 4 按需回查，不全量重复。

## 图表变更高亮（强制）

> 当方案涉及对已有流程/交互/状态的新增或修改时，Mermaid 图中**本次新增或修改的部分必须使用红色背景高亮**，使评审者能一眼看出改动点。

**高亮样式定义**：

| 图表类型 | 高亮方式 | 样式 |
|----------|---------|------|
| `flowchart` | `classDef` + `:::` 语法标注节点 | `fill:#ffcccc,stroke:#ff0000,stroke-width:2px` |
| `sequenceDiagram` | `rect rgb(255, 204, 204)` ... `end` 包裹交互块 | 浅红背景矩形 |
| `stateDiagram-v2` | `classDef` + `class 状态名 className` 语法标注状态 | `fill:#ffcccc,stroke:#ff0000,stroke-width:2px` |
| `flowchart`（联动图） | 同 flowchart，对新增/修改的联动节点标注 | 同上 |

**适用场景**：

- **二次开发 / 功能扩展**：在已有流程基础上新增环节、修改分支逻辑、新增状态或跳转
- **技术改造**：对已有链路的调整（增加步骤、变更调用目标、修改状态机）
- **不适用**：全新功能（所有节点都是新增的情况下无需标注，避免全图变红失去对比意义）

**标注规则**：

1. 图中已有节点/交互保持默认样式，**仅对本次新增或修改的节点/交互添加高亮**
2. 新增节点与修改节点使用相同样式（均为红色背景），通过节点文字区分（如 `[新增: xxx]` 或注释说明）
3. 图表下方用 `> 🔴 红色背景 = 本次新增/修改` 添加图例说明
4. 具体样式示例见 `references/examples/技术方案模板-示例.md`「变更高亮示例」章节

## 纪律（贯穿全流程）

- **不编造**外链/系统名/Topic/表结构 — 未提供用 `TBD`
- **不手写表格骨架** — 统一从 `技术方案-表格模板.md` 复用
- **约束优先级**：本文件 > 骨架 `> 提示：` 行
- **【强制】知识库为唯一事实来源**：以下三类产出**必须**以 `scripts/call_kb.py` 检索或直接 Read 本地知识库（`kb_root`）的结果为唯一依据，**不得**凭经验、记忆或臆测自行定义：
  1. **规范类**：接口规范、数据库规范、接口字段命名、路径命名、数据库字段命名等 — 所有命名与格式以知识库规范条文为准
  2. **公共组件与外部依赖类**：已有公共组件、中间件、框架、SDK、三方服务 — 选型和接口设计中涉及通用能力时，**必须先检索知识库确认是否已有现成组件**；知识库中存在的**必须复用**，不得重复建设；知识库中不存在的方可设计新方案，并在方案中注明「知识库未收录，新建」
  3. **现有业务类**：业务域划分、系统边界、已有接口、已有流程 — 系统边界划分、接口复用/新增判断、业务流程衔接**必须以知识库中的业务域文档和接口文档为准**；不得脱离知识库自行假设系统职责或虚构已有接口
  - **例外 — 二次开发场景**：当 `.project-context.md` 存在时（即 Step 0.5b 成功执行），上述三类产出**允许以项目现有代码实践为优先依据**。具体规则：
    - **规范类**：项目代码中已形成的命名规范、字段类型约定优先；项目中未体现的规范仍从知识库拉取
    - **公共组件类**：项目已采用的组件/框架**必须继续复用**；知识库中有而项目未采用的，按知识库要求评估是否引入
    - **现有业务类**：项目实际的系统边界、接口、流程**优先于知识库文档**（代码为准）
    - **冲突标注**：项目实践与知识库规范不一致时，在方案中标注「与知识库规范 {xxx} 存在差异：{描述}，遵循项目现有实践」
- **违反判定**：方案中出现未经知识库检索确认的规范引用、组件选型或业务假设，视为不合格，Step 4 自检须标记为 ❌ 并修正
- **【强制】信息获取渠道限制**：方案设计过程中**不得**使用编辑器内置文件系统工具（Read/Glob/Grep/Bash）直接读取或搜索目标项目的源代码文件。信息获取渠道严格限定为：
  - **规范与知识文档** → `scripts/call_kb.py` + Read 本地 KB 目录（`kb_root`）
  - **目标项目代码** → GitNexus MCP tools（query/context/impact/cypher/route_map）
  - **TAPD 需求内容** → `call_tapd_mcp.py`
  - **允许 Read 的本地文件**（仅限以下白名单）：
    1. Skill 自身模板文件（`assets/`、`references/`）
    2. Skill 工作文件（`.req-summary.json`、`.kb-map.md`、`.terminology-cache.md`、`.gitnexus-cache.md`、`.project-context.md`、`.service-doc-plan.json`、`.tapd-req-full.md`）
    3. TAPD 下载资产（`tapd-assets/` 目录下的图片和附件文件）
    4. 工作流管道输入文件（`01-需求分析.md`、`02-服务拆分.md`）
    5. 方案正式产物文件（`03-技术方案*.md`，用于自检和补全）
    6. **知识库文件**（`kb_root` 配置目录下符合 `include_globs` 的 `.md` 文件，路径从 `scripts/kb.config.json` 读取）
  - **违反判定**：使用 Read/Glob/Grep 读取上述白名单外的本地文件（如 `.java`/`.proto`/`.xml`/`.gradle` 等源代码文件，或非 `kb_root` 目录下的项目文档）视为违规

## 工作流

> **Step 0a-pre 需求分析提取（强制）** → Step 0a service-split 解析（可选）→ **【模式判断】** → **Step 0b GitNexus 业务知识检索（强制，当 GitNexus 可用时）** → Step 0c 知识库探测（强制）→ Step 0.5 TAPD拉取+项目代码探测（条件触发） → Step 1~2 分析决策 → Step 3 分段生成 → **Step 3.5 业务完整性回溯（强制）** → Step 4 规范自检 → 生成目录 → 清理工作文件
>
> **模式判断**（Step 0a 完成后立即执行）：
> - `02-服务拆分.md` 存在且含 ≥2 个主责/协同服务 → **多服务分档模式**：为每个服务独立生成 `03-技术方案-{服务名}.md`，Step 3 按服务循环执行
> - 其他情况 → **单文件模式**：输出 `03-技术方案.md`，Step 3 按功能点拆分（原有行为）

### Step 0a-pre：需求分析提取（强制）

检查工作流目录是否存在 `01-需求分析.md`（路径从用户上下文或 dev-workflow 传入获取）。

**提取原则**：只提取结构化要素，不保留叙述性文字；原文体量无论多大，提取结果控制在 ~800 token 以内。

**后续使用**：Step 1 输入评估、Step 3 各子段落动笔前、Step 3.5 业务完整性回溯，均读 `.req-summary.json`，**不重复读原文**。

**若不存在**：写入 `{"source": null, "functions": [], "business_rules": [], "boundary_constraints": [], "nonfunctional": []}`，在 Step 1 中标注"无需求分析文档，功能清单将从用户描述推导"，**不阻断流程**，但后续 Step 3.5 的①回溯项跳过。

### Step 0a：解析 service-split 输入（可选）

检查当前工作流目录是否存在 `02-服务拆分.md`（路径：`{工作流目录}/02-服务拆分.md`，工作流目录从用户上下文或 dev-workflow 传入获取）。

**若存在**，读取并提取以下内容，缓存为内部工件"服务拆分摘要"：

| service-split 节 | 映射到技术方案 |
|-----------------|--------------|
| 一、功能清单摘要 | Ch 2 功能点清单（直接复用，不重新列举） |
| 二、全局业务流程（触发点 + 端到端时序 + 关键数据流 + 异常路径） | Ch 1 背景与目标 + Ch 6.x.1 业务流程 |
| 三、服务边界定义（每服务：职责、包含/不包含、对外暴露、依赖上游） | Ch 4 涉及的服务/系统 |
| 四、本次各服务改动清单（新增接口数、修改接口数、新增 Service 数、DB 变更） | Ch 6 功能设计范围 + Ch 7 接口清单规模 |
| 五、服务改动总览（汇总表） | Ch 4 系统边界汇总 |

**【模式判断】提取完成后立即执行**：

**第一步：服务发现（容忍角色标签变体）**：

从 `02-服务拆分.md` 中定位"服务改动总览"表（搜索包含 `服务名称`、`角色` 等列表头的 Markdown 表格，**不依赖固定章节号**，因为实际文档可能未严格遵循模板编号）。统计角色列**包含**以下关键词的服务行：

| 角色匹配规则 | 示例 |
|-------------|------|
| 包含 `主责` | `主责` |
| 包含 `协同` 或以 `协同` 开头 | `协同`、`协同改动`、`协同-改枚举`、`协同-前端`、`协同(只读)` |

**排除**角色为 `被调用`、`被调用方`、`排除`、`仅调用` 的服务行（这些不产生设计工作量）。

**第二步：模式判定 + 用户确认**：

- **≥ 2 个服务** → 进入**多服务分档模式**，构建服务列表写入 `.service-doc-plan.json`（结构和用户展示模板见 `references/work-file-templates.md`「service-doc-plan」节）。向用户展示输出文件列表，确认后继续。
- **1 个服务** → 单文件模式，`.service-doc-plan.json` 中 `mode: "single"`。
- **0 个服务**（表格不存在或匹配不到）→ **不要静默降级**。检查 `02-服务拆分.md` 中是否在"四、本次各服务改动清单"或以 `### ` 标题列出了多个服务子节。若存在 ≥2 个服务名 → **必须向用户确认**：输出检测到的服务列表，询问"服务拆分文档中检测到 {N} 个服务，是否按多服务分档生成独立技术方案？"，等待用户选择后再决定模式。确认为单文件后，`.service-doc-plan.json` 中 `mode: "single"`。

**若不存在**：标注"无 service-split 输入，将从需求描述全量推导"，`mode: "single"`，继续执行 Step 0b（按下方降级链确定查询输入）。

### Step 0b：GitNexus 业务知识检索（**强制**，当 GitNexus 可用时执行）

> **为什么强制**：`02-服务拆分.md` 只描述了"应该改什么"，但不能保证业务对象的实际数据来源被完整识别。GitNexus 代码图谱能揭示：业务对象字段在哪个流程中被写入（**写入流**）、谁调用该接口（**调用方**）、哪些字段在某些场景下可能为 null（**数据链路假设**）。跳过此步是 v2.0 方案出现"remitOrderId 假设非空"根本原因。
>
> **与 Step 0.5b 的关系**：Step 0b 和 Step 0.5b **目的和数据视角不同，不互相替代**。Step 0b 关注业务假设验证（产出 `.gitnexus-cache.md`，供 Step 3.5 回溯使用）；Step 0.5b 关注项目架构探测（产出 `.project-context.md`，供 Step 3 生成使用）。即使两步执行了类似的 GitNexus 查询，两份文件**必须各自独立生成**。

**查询输入来源**（按优先级降级）：

| 优先级 | 条件 | 输入来源 | 查询范围 |
|--------|------|---------|---------|
| 1 | Step 0a 成功（有 service-split） | service-split 中识别的服务和改动点 | 查询 A~E 全部执行 |
| 2 | Step 0a-pre 成功（有 .req-summary.json） | `.req-summary.json` 中的 `functions[].name`、核心业务对象、`interface_fields` 涉及的领域概念 | 查询 A~E 全部执行，查询 C 的接口列表从 `interface_fields` 推断 |
| 3 | 均无（skill 独立运行，仅有用户原始输入） | 用户提供的需求描述/关键词/TAPD内容 | 查询 B~E 执行（从用户描述提取关键词/接口/服务名/改动目标），跳过 A（业务对象写入流分析依赖结构化输入，无法可靠识别全部核心业务对象） |

> **注意**：优先级 3 场景下，查询 A 被跳过，方案中涉及业务对象字段存在性假设未经写入流验证，须在 Ch 1 "风险与待澄清" 中注明。

对识别到的**需要改动的每个服务**（非"排除"角色），**按以下顺序强制执行查询**：

**查询 A — 业务对象写入流（最重要，防止"数据链路假设"错误）**

对每个方案中涉及的核心业务对象（如退款订单、充值订单、审核批次等），必须查询**创建/初始化**它的流程，而不仅仅是读取它的流程：

```
mcp__gitnexus__query(
  query="{业务对象名} 创建 保存 初始化",
  goal="找到创建该业务对象的所有入口及字段赋值情况"
)
```

**关键原则**：如果某字段在"正常审核流程"中是通过读接口获取的，必须额外确认：**在该字段写入时（创建/更新），是否存在该字段为 null / 空 / 使用替代值的场景**。有此类场景时，必须在方案中设计分支处理逻辑，不得假设字段非空。

**查询 B — 涉及接口的调用链（确认接口实际行为）**：
```
mcp__gitnexus__query(query="{涉及接口名}", goal="找到该服务的核心调用链和对外接口")
```

**查询 C — 确认已有接口签名**（来自 service-split 第三节"对外暴露"中列出的接口）：
```
mcp__gitnexus__context(name="{接口方法名或类名}", file_path="{Controller/Service路径}")
```

**查询 D — 跨服务调用路径**（如有多个服务需要交互）：
```
mcp__gitnexus__cypher(query="MATCH (a)-[:CodeRelation {type:'CALLS'}]->(b) WHERE a.name='{ServiceA}' RETURN b.name, b.filePath")
```

**查询 E — 影响范围分析**（对本次需要修改的接口/类执行）：
```
mcp__gitnexus__impact(target="{需要修改的类或方法名}", direction="upstream")
```

将结果写入 `{工作流目录}/.gitnexus-cache.md`（模板见 `references/work-file-templates.md`「gitnexus-cache」节）。

**【产出门禁】**：Step 0b 执行完毕后，必须确认 `{工作流目录}/.gitnexus-cache.md` 已写入且包含全部 5 个 section 标题（业务对象写入流分析 / 涉及服务调用链 / 已有接口签名 / 影响范围分析 / 数据链路假设验证结论）。文件未生成时**不得进入 Step 0c**。

**优先级 3 降级产出规则**（仅有用户原始输入时）：

Query A 和数据链路假设验证因缺少结构化输入而跳过时，`.gitnexus-cache.md` 仍须生成，对应 section 按以下规则填写：

| section | 填写内容 |
|---------|---------|
| 业务对象写入流分析 | `⚠️ 跳过：当前为独立运行模式，无结构化业务对象列表，写入流未验证` |
| 涉及服务调用链 | 正常填写（从用户描述提取关键词执行 Query B） |
| 已有接口签名 | 正常填写或标注 `⚠️ 降级：从用户描述推断，覆盖率不保证` |
| 影响范围分析 | 正常填写（执行 Query E） |
| 数据链路假设验证结论 | `⚠️ 跳过：Query A 未执行，数据链路假设未验证，需人工复核` |

同时须在 Ch 1「风险与待澄清」中注明：**因无结构化输入，方案中涉及业务对象字段存在性假设未经写入流验证，需人工复核。**

**GitNexus 不可用时**：标注 `⚠ GitNexus 不可用，Ch 4 服务边界依赖 service-split 文档推断，6.x.3 接口签名待人工核实，业务对象写入流未验证`，**不终止流程**，继续进入 Step 0c。但必须在 Ch 1 "风险与待澄清" 中注明：**因 GitNexus 不可用，方案中涉及业务对象字段存在性假设未经代码验证，需人工复核**。

### Step 0c：知识库探测（强制，原 Step 0）

1. **读取配置**：`Read scripts/kb.config.json`，获取 `access_mode` / `kb_root` / `kb_index_file` / `include_globs` / `exclude_globs`。**不硬编码路径，所有路径从配置读取。**
2. **解析全局索引**：
   - `access_mode=local`：`Read {kb_root}/{kb_index_file}`（如 `Read /path/to/knowledge-base/_INDEX.md`）
   - `access_mode=remote_mcp`：`python3 scripts/call_kb.py read -f {kb_index_file}`
   - **成功** → 解析索引内容，按下方分类整理为 `.kb-map.md`（此阶段**仅解析索引、不拉取具体文件**，具体内容在后续设计阶段按需 `search`/`Read` 获取）
   - **失败/为空** → 进入降级
3. **降级（仅 `kb_index_file` 不可用时）**：
   - `access_mode=local`：`python3 scripts/call_kb.py list --recursive` 列出 `kb_root` 下所有符合 `include_globs` 的文件
   - `access_mode=remote_mcp`：`python3 scripts/call_kb.py list --path / --recursive`
   - **降级成功**（返回文件列表）→ 按下方分类整理为 `.kb-map.md`，并告知用户：仅通过目录扫描构建知识库地图，可能遗漏部分文档分类信息
   - **降级也失败**（list 为空或脚本报错）→ **立即终止方案生成流程，不得进入 Step 1**（见第 5 点异常处理）

#### 0.5b 项目代码探测（GitNexus）

> **与 Step 0b 的关系**：Step 0.5b 的项目代码探测（3a~3e）与 Step 0b 的 Query A~E **查询目的和数据视角不同，不互相替代**：
> - Step 0b 关注**业务假设验证**：对象字段是否可能为空、接口复用状态、数据链路假设
> - Step 0.5b 关注**项目架构探测**：枚举值、代码模式、分层结构、可复用数据模型
>
> 即使 Step 0.5b 执行了类似的 GitNexus 查询，`.gitnexus-cache.md`（Step 0b 产出）和 `.project-context.md`（Step 0.5b 产出）**必须各自独立生成**，不得以一方替代另一方。

**触发**：需求明确涉及对某个已有项目的二次开发 / 功能扩展 / 技术改造。判断依据：
- 用户明确指定了目标项目/代码仓库
- 需求内容提及具体系统名且该系统有对应代码仓库
- 用户要求「基于现有项目设计」或类似表述

**执行步骤**：

1. **确认可探测**：调用 `mcp__gitnexus__list_repos` 获取所有已索引项目列表。未索引任何项目 → 告知用户，跳过本步骤。
2. **跨项目调用链发现**：
   - 2a. 若需求涉及具体 API 路径 → 在所有已索引项目中执行 `mcp__gitnexus__route_map`（带 `route` 参数），查找该路径的所有 handler
   - 2b. 若需求涉及具体关键词/符号 → 在所有已索引项目中执行 `mcp__gitnexus__query`（以需求核心关键词为 query），查找相关执行流程
   - 2c. 将命中的所有项目纳入「探测项目组」（若用户已指定目标项目且未命中其他项目，则探测项目组仅含该项目）
3. **对探测项目组中每个项目，分别执行**：
   - 3a. **查询相关执行流程**：调用 `mcp__gitnexus__query`，以需求核心关键词（业务动作、领域概念）为 query，`repo` 指定当前项目。提取 Top 5 相关 process 及其 symbols
   - 3b. **深入关键符号**：对 3a 中与需求最相关的 2~3 个核心符号，调用 `mcp__gitnexus__context` 获取完整上下文（调用者、被调用者、所属模块、文件位置）
   - 3c. **影响分析**（仅改造/扩展场景）：对需要修改的符号调用 `mcp__gitnexus__impact`（`direction: "upstream"`），评估变更 blast radius
   - 3d. **接口映射**（仅涉及 API 的场景）：调用 `mcp__gitnexus__route_map`（可带 `route` 过滤），查看现有路由、handler、consumer 关系
   - 3d-2. **异步回调链路追踪**（涉及异步交互时强制）：当发现当前项目通过异步方式（orderSender/MQ/回调/事件/RPC异步调用）与其他系统交互时：
     - 将回调来源系统纳入「探测项目组」
     - 追踪回调入口（Controller/Listener）、回调报文格式、回调触发的后续流程
     - 在 `.project-context.md` 的「调用链路总览」中标注异步边界
     - **方案生成时须为回调处理逻辑生成独立功能点**（至少含：回调入口路由、报文解析、状态机驱动、异常处理）
   - 3e. **项目级业务约定扫描**：通过 `mcp__gitnexus__cypher` 或 `mcp__gitnexus__query` 扫描以下约定（以项目实际代码为准，非知识库规范）：
     - **错误码**：搜索 ErrorCode/BizException/错误码枚举类，确认：数据类型（字符串数字/英文枚举/数字）、编号规则（分段/分模块）、已有值样例 5~10 个
     - **交易类型(tradeType)**：搜索 TradeType 枚举，确认：数据类型（string/int）、已有值清单
     - **接口标识(interfaceCode)**：搜索 InterfaceEnum 等，确认：命名风格、已有值
     - **其他核心枚举**：如 tradeStatus、liquidationChannel 等，确认数据类型和取值
     - **Proto 字段类型约定**：确认项目中同类字段（如状态码、类型码）在 .proto 中使用的 PB 类型
     - **可复用数据模型**：搜索与需求涉及业务对象相关的 Entity/DO/DTO/Table 定义类，确认：已有表结构（字段名、字段类型、索引）、已有 DTO/VO 字段清单；写入 `.project-context.md`「项目级业务约定」表新增行「可复用数据模型」
4. **调用链路整合**：标注项目间的调用顺序（如 入口层 → 执行层），识别各项目在完整请求链路中的职责
5. **产出写入** `.project-context.md`（多项目格式，见下方模板）

**产出**：写入 `{工作流目录}/.project-context.md`（模板见 `references/work-file-templates.md`「project-context」节）。

**单项目场景简化**：若探测项目组仅含 1 个项目，可省略「调用链路总览」章节，直接输出该项目的探测结果。

**异常（不终止）**：GitNexus 工具调用失败或项目未索引 → 告知用户，跳过本步骤，后续仅依赖知识库。在 `.project-context.md` 中记录「探测失败：{原因}」。

在 `.project-context.md` 写入完成后，对照 `.req-summary.json`（或用户原始需求）逐项检查：

#### 多服务分档模式（`mode: "multi-service"`）

**第一步：生成架构总览文档（`03-技术方案.md`）**

架构总览是跨服务视角的"合同文档"，在逐服务生成之前输出（内容规格见 `references/work-file-templates.md`「architecture-overview」节）。

**第二步：逐服务生成实施方案（`03-技术方案-{服务名}.md`）**

遍历 `.service-doc-plan.json` 的服务列表，按`主责 → 协同`顺序，**对每个服务完整执行一轮子段落 1~3**，生成独立文件后再进入下一个服务。

```
for each service in services:
    动笔前：Read .terminology-cache.md（已有则加载，首次生成则在子段落 1 首次触发术语检索时创建）
    子段落 1：Ch 0~5
      - Ch 1 背景：一句话说明本服务在全局流程中的角色，引用"见架构总览 Ch 1"
      - Ch 4：仅写本服务的上下游边界（调用哪些服务/被哪些服务调用）；跨服务接口契约注明"见架构总览 Ch 6"
      - Ch 5：只写归属本服务的 DB 表；若 DB 变更已在架构总览定义，注明"见架构总览 Ch 5，本服务无新增"
    子段落 2：Ch 6~7（仅写当前服务的功能点，范围来自 service-split 第四节该服务的改动清单）
      - 6.x.3 外部接口：若该接口是跨服务接口，注明"契约见架构总览 Ch 6.{N}"，不重复定义
      - 6.x.5 接口设计：只设计本服务内部新增接口；跨服务接口契约已在架构总览定义，此处引用
    子段落 3：Ch 8 + 文末（外部依赖、保障、待澄清——仅当前服务视角；整体上线顺序见架构总览 Ch 8）

    向用户展示：✅ {服务名} 实施方案已生成：{output_file}，确认后继续下一个服务
```

**多服务间共享约定**：
- **架构总览为跨服务内容的唯一权威来源**：端到端流程、完整 DDL、跨服务接口契约只在 `03-技术方案.md` 定义，各服务文档引用不重复定义

- **Ch 5 数据库设计**：只写归属当前服务的表；若多服务共享某张表，架构总览已完整定义，服务文档中注明"复用，见架构总览 Ch 5"
- **公共组件选型**（Ch 3）：第一个服务完成 Ch 3 选型后，后续服务直接引用结论，不重复对比

- 6.x.5 接口设计结构：**必须包含**协议代码（Proto/REST）+ 字段说明表 + 错误码表（code 字符串 + msg 字符串）；协议代码与字段说明表须互为镜像（字段顺序、名称、类型一一对应）；**不生成**接口处理流程（伪代码/调用树）。**协议代码格式规则**：
  - **Protobuf**：每个 `message` 定义中，字段行按列对齐：`{optional/repeated}  {type}  {name}  = {number};  // {comment}`，各列之间用空格补齐对齐（格式示例见「技术方案-表格模板.md」）；字段顺序须与下方字段说明表完全一致；嵌套 message 缩进 2 空格。**Response message 仅定义 `basic`（ResponseBasic）+ 业务数据字段，不新增 code/msg/scode/error_code 等字段**（错误码由 ResponseBasic 承载）
  - **REST JSON**：请求/响应 JSON 示例使用 2 空格缩进；字段顺序须与下方字段说明表完全一致；每个字段值后以行尾注释标注类型和含义（如 `"amount": 1000  // long, 金额(分)`）
  - **字段说明表**：字段行出现顺序必须与协议代码中字段声明顺序完全一致，不得重新排序
  - **错误码表**：code 列的值必须与协议代码或接口规范中实际使用/抛出的错误码一致
- **【强制】接口变更分类**：每个功能点动笔 6.x.3/6.x.5/6.x.7 前，先将本功能点涉及的每个接口/数据模型分类为：

  - **变更**：项目中已存在但需修改（加字段/改逻辑/改入参出参）→ 6.x.5 仅输出变更增量（标注「扩展已有接口 {名称}」，仅列新增/修改字段和新增错误码，不重复已有字段）；6.x.3 含变更部分的时序
  - **仅调用**：项目中已存在且本功能点不修改，仅作为上下游调用 → 6.x.5 不输出（写「本功能点仅调用已有接口 {名称}，不涉及接口变更」）；6.x.3 中以单行调用标注（`A->>B: 调用已有接口 {名称}`），不展开接口细节
  - 分类依据：`.project-context.md`「现有接口」中的「可复用/需扩展」列 + 需求中明确的改动清单；无 `.project-context.md` 时按需求描述和知识库接口文档判断
