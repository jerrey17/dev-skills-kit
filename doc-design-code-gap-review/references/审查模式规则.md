# 审查模式规则

本 skill 先识别审查模式，再按模式装配事实清单、对齐矩阵与报告章节。

## 1. 模式定义

| 模式ID | 输入组合 | 基线层 | 对齐层 | 审查对 |
| --- | --- | --- | --- | --- |
| `REQ_DESIGN` | 需求文档 + 技术文档 | 需求 | 技术文档 | 需求 -> 技术文档 |
| `DESIGN_CODE` | 技术文档 + 代码 | 技术文档 | 代码 | 技术文档 -> 代码 |
| `REQ_CODE` | 需求文档 + 代码 | 需求 | 代码 | 需求 -> 代码 |
| `REQ_DESIGN_CODE` | 需求文档 + 技术文档 + 代码 | 串联双基线 | 串联双对齐 | 需求 -> 技术文档；技术文档 -> 代码 |

说明：

- `REQ_DESIGN_CODE` 不做三方平级混合对比，只按两个审查对顺序执行
- “技术文档”包括技术方案、设计文档、概要设计、详细设计等

## 2. 模式识别规则

按以下顺序判断：

1. 同时存在需求文档、技术文档、代码，识别为 `REQ_DESIGN_CODE`
2. 存在需求文档、技术文档，识别为 `REQ_DESIGN`
3. 存在技术文档、代码，识别为 `DESIGN_CODE`
4. 存在需求文档、代码，识别为 `REQ_CODE`
5. 若以上均不满足，则不是正式模式

识别模式后，还需同时满足：

- 审查对象可收敛到接口、模块、类、方法、需求编号中的至少一项
- 若模式包含代码，文档与代码之间至少能建立初步对应关系

## 3. 模式与产物映射

| 模式ID | 事实清单 | 对齐矩阵 | 报告重点 |
| --- | --- | --- | --- |
| `REQ_DESIGN` | 需求事实清单、技术事实清单 | 需求-技术对齐矩阵 | 方案是否承接需求 |
| `DESIGN_CODE` | 技术事实清单、代码事实清单 | 技术-代码对齐矩阵 | 实现是否落地技术文档 |
| `REQ_CODE` | 需求事实清单、代码事实清单 | 需求-代码对齐矩阵 | 实现是否直接满足需求 |
| `REQ_DESIGN_CODE` | 需求事实清单、技术事实清单、代码事实清单 | 需求-技术对齐矩阵、技术-代码对齐矩阵 | 链路断点、方案遗漏、代码额外实现 |

## 4. 模式与报告章节映射

所有模式都必须包含：

- 审查概览
- 模式与来源摘要
- 总体结论
- 审查对差异明细
- 需要补充上下文的事项
- 修正建议

仅当审查对齐层包含代码时，应重点填写：

- 代码额外实现项

仅 `REQ_DESIGN_CODE` 额外强调：

- 链路总评
- 需求 -> 技术文档总体对齐情况
- 技术文档 -> 代码总体对齐情况

## 5. 状态判定规则

### `DONE`

满足以下条件：

- 已识别正式模式
- 审查范围已收敛
- 关键维度证据完整
- 已完成全部所需事实清单、对齐矩阵与报告
- 不存在影响结论成立的关键缺口

### `DONE_WITH_CONCERNS`

满足以下条件：

- 已识别正式模式
- 已完成主要审查产物
- 存在明显差异、中高风险或较多需修正项
- 但整体证据足以支撑主要结论

### `NEEDS_CONTEXT`

满足以下条件：

- 已识别正式模式
- 但存在部分证据不足、文档细节不够、代码范围不完整或关键来源未能定位
- 仍可输出部分结论，但必须明确受影响范围

### `BLOCKED`

满足以下任一条件：

- 无法识别为正式模式
- 无法收敛审查对象
- 模式包含代码，但找不到与文档对应的基本实现范围
- 缺失输出路径和项目根目录，无法落盘

## 6. 执行约束

- 模式一旦识别完成，后续步骤必须围绕该模式展开，不得临时切换基线层
- 不为未纳入当前模式的来源类型生成空白事实清单或空章节
- 若模式包含两个审查对，必须先完成第一个审查对，再执行第二个审查对
