# service-split — 服务拆分

## 目标

基于需求分析文档（或用户直接提供的需求描述），梳理端到端业务流程，确定各服务的职责边界和改动范围，输出可直接被技术方案和编码阶段消费的结构化拆分文档。

这个 skill 做五件事：
1. 读取需求信息（分析文档或用户描述）
2. 梳理端到端全局业务流程
3. 扫描本地代码仓库结构（可选，仓库不存在时标注）
4. 结合知识库检索确定服务边界
5. 输出结构化拆分方案，经人工确认后写入 `02-服务拆分.md`

这个 skill **不负责**：
- 更新 `current.md`
- 技术方案设计
- 决定是否进入下一阶段（由 dev-workflow 负责）

| 主项目路径 | 询问用户（绝对路径或相对当前工作目录的路径）；用户说"没有本地仓库"则跳过 |
| 输出目录 | 默认与需求分析文档同目录；无分析文档��放当前工作目录 |

## 单服务快速路径

**判断时机**：Step 1 采集信息完成后，立即判断是否为单服务需求。

**判断标准**：满足以下全部条件：
- 所有功能点均归属同一服务，无跨服务 RPC/Feign/MQ 调用
- 需求描述中无"调用 XX 服务"、"依赖 XX 接口"等跨服务表述
- 知识库/代码结构未发现其他服务持有相关入口

**单服务路径**：Step 1 → Step 3（仅扫描该服务仓库）→ Step 5（简化输出）→ Step 6 → Step 7

简化输出格式：
```
服务边界分析结论：单服务需求

涉及服务：{服务名}（✅ 已扫描 / ⚠ 未找到）
职责范围：{本次涉及的功能点}
不涉及其他服务：{说明原因，如"所有改动均在 XX 服务内部完成，无跨服务调用"}
改动清单：新增接口 ×N，修改接口 ×N，DB 变更 ×N
```

确认后直接写入 `02-服务拆分.md`，跳过时序图和多服务边界分析。

## 流程概览

```text
Step 1  采集需求信息 → 【判断单/多服务】
                        ├── 单服务 → Step 3 → Step 5（简化）→ Step 6 → Step 7
                        └── 多服务 → Step 2 → Step 3 → Step 4 → Step 5 → Step 6 → Step 7
```

## Step 1 — 采集需求信息

### 来源 A：已有需求分析文档

读取 `01-需求分析.md`，提取：
- **功能清单**：本次需求新增或修改的功能点
- **业务对象**：涉及的核心数据实体（用户、订单、账户等）
- **业务动作**：主要的业务操作（绑卡、扣款、查询等）
- **边界约束**：需求中明确提到的依赖服务、外部接口、限制条件

### 来源 B：用户直接描述

直接使用用户提供的需求描述，提取上述四类信息。无需强制要求先完成需求分析。

如果用户描述过于简短（不足以判断服务归属），补问：
> "这个需求主要涉及哪类业务操作？（如：用户信息变更 / 支付流程 / 订单状态）"

---

## Step 2 — 梳理端到端全局业务流程

**在进行服务拆分之前，先梳理完整业务链路。** 这是保持全局观的核心步骤，技术方案和编码阶段遇到跨服务问题时应回此节定位。

梳理四个维度：

**① 触发点**：谁触发、何种条件触发（如"用户在 App 发起还��"）

**② 端到端时序**：从触发到最终结果，各服务��介入顺序排列，每步说明：
- 触发方和接收方
- 发生的动作
- 该服务内部的主要处理逻辑

**③ 时序图（必须生成）**：用 Mermaid `sequenceDiagram` 把端到端时序图形化，要求：
- 所有涉及服务/系统均作为参与方（participant）
- 主链路的请求和响应均标注
- 涉及异步/MQ 的用注释或 `Note` 标注
- 有条件分支的用 `alt` 块标注（如：成功/失败路径）
- ���标：读者一眼看清整个链路，不需要再读文字流程

**④ 关键数据流**：数据在服务间如何流转（HTTP / RPC / MQ / DB 读写），以及异常路径的处理方式

---

## Step 3 — 识别本地代码仓库

对 Step 2 中识别到的每个服务，尝试在本地找到对应代码仓库，并标注状态。

### 仓库状态三种情况

| 状态 | 说明 | 处理方式 |
|------|------|---------|
| ✅ 已扫描 | 本地找到仓库，已扫描代码结构 | 扫描 Controller/Service 层，了解已有接口和模块 |
| ⚠ 未找到本地仓库 | 服务需要改动，但本地无对应仓库 | 改动范围依据知识库推断，在文档中标注需人工核实 |
| — 仅调用无需改动 | 只是调用方，不需要修改代码 | 标注角色，无需扫描 |

### 扫描规则（仅对 ✅ 已扫描 的仓库）

只读目录结构，不读具体文件内容：
1. `src/main/java/` 下顶层包结构（domain/module 划分）
2. Controller 层目录（已有接口范围）
3. Service 层目录（已有服务）
4. `pom.xml` 或 `build.gradle`（模块依赖关系）

---

## Step 4 — 知识库检索

目标：找到各功能点对应的服务归属和边界约束依据，优先使用代码图谱的实际调用关系，再用本地知识库补充规范依据。

### 检索工具顺序

- 第一优先级：GitNexus 代码图谱（反映真实调用关系，优于文档）
  - `mcp__gitnexus__query`：按业务关键词检索相关执行流程
  - `mcp__gitnexus__context`：查看具体符号的调用者/被调用者关系
  - `mcp__gitnexus__route_map`：查看 API 路由与 handler 归属
- 第二优先级：本地知识库（通过 `tech-solution-design/scripts/call_kb.py` 访问，配置见 `scripts/kb.config.json`）

**GitNexus 不可用时**：跳过第一优先级，直接从第二优先级开始，在"六、知识库空白"节标注 `⚠ GitNexus 不可用，服务调用关系依赖知识库文档推断`。

**本地知识库不可用时**（`call_kb.py` 执行失败或 `kb.config.json` 未配置）：跳过第二优先级，在"六、知识库空白"节标注 `⚠ 本地知识库不可用，服务边界依赖代码结构推断`，继续基于代码结构和需求描述完成拆分。

### 检索策略

**第一阶段 — GitNexus 代码图谱检索**（优先执行）：

基于 Step 1 的业务动作和业务对象，依次执行：

1. **查执行流程**：`mcp__gitnexus__query(query="{业务动作} {业务对象}", goal="找到相关服务的调用流程和入口")`
2. **查路由归属**（涉及 API 时）：`mcp__gitnexus__route_map(route="{已知路径前缀}")`
3. **查调用链**（有核心类/方法时）：`mcp__gitnexus__context(name="{核心类或方法名}")`

命中后提取：哪个服务持有入口、调用了哪些下游服务、已有哪些接口。

**第二阶段 — 本地知识库检索**（补充规范依据）：

GitNexus 已覆盖调用关系后，用本地知识库补充：

```bash
python3 ~/.claude/skills/tech-solution-design/scripts/call_kb.py search -k "{业务对象} 服务 接口归属"
python3 ~/.claude/skills/tech-solution-design/scripts/call_kb.py search -k "{业务动作} 业务规则 流程"
python3 ~/.claude/skills/tech-solution-design/scripts/call_kb.py search -k "{主服务} 调用 {下游服务}"
```

命中后可用 `read -f {相对路径}` 读取完整文档片段确认。

**停止条件**：满足以下 2 项即停止：
- 已确认主要功能点的服务归属
- 已了解主要跨服务依赖关系

**检索上限**：GitNexus 最多 3 次，知识库 search 最多 3 次，合计不超过 6 次，需求简单时更少。

### 整理检索结果为四类证据

- **服务归属证据**：哪个功能点属于哪个服务，依据哪个文档
- **边界约束证据**：服务的包含/不包含范围
- **接口证据**：已有接口可复用 or 需要新增
- **跨服务依赖证据**：哪些服务存在调用关系

知识库无命中时：不中断流程，在文档"知识库空白"节标注，继续基于代码结构和需求描述完成拆分。

## Step 5 — 生成拆分建议

综合 Step 1-4，向用户展示拆分建议。**此步只输出文本，不写任何文件。**

输出格式：

```
服务拆分建议：

── 全局业务流程 ──
触发点：{触发方} 发起 {业务动作}
流程：
  1. {触发方} → {服务A}：{动作}
  2. {服务A} → {服务B}：{动作}
  3. {服务B} → {结果}
关键数据流：{数据} 从 {来源} 流向 {目标}（{形式}）

时序图（Mermaid）：
[内联 sequenceDiagram，覆盖主链路及关键异常分支]

── 功能点归属表 ──
| 功能点 | 主责服务 | 协同服务 | 归属依据 |
每行一个功能点，主责服务有且只有一个

边界冲突检测：
  多服务认领同一功能点：{有/无，若有列出}
  功能点无人认领：{有/无��若有列出}
  边界与时序图一致：{是/否，若否列出不一致处}

── 各服务边界 ──
{服务名称}（本地：✅ 已扫描 / ⚠ 未找到 / — 无需）：
  职责：{业务域}
  包含：{本次涉及的功能点}
  不包含：{明确排除}
  依据：{知识库文档 / 代码结构推断}

── 本次改动（按服务） ──
{服务名称}（✅/⚠/—）角色：主责 / 协同 / 被调用 / 排除
  改动：新增接口 ×N，修改接口 ×N，新增 Service ×N，DB 变更 ×N
  ⚠ 本地未找到时：改动范围为推断，需对应负责人核实

{服务名称}（排除）：{排除原因}

── 服务改动总览 ──
共涉及 N 个服务：主责 1 个，协同 N 个，被调用 N 个，排除 N 个
本地仓库就绪：N 个；未找到：N 个

── 知识库空白 ──
{功能点}：{原因}（待人工确认）
```

明确询问：
> "以上全局流程、时序图和服务拆分是否准确？边界冲突检测结果是否符合预期？是否需要调整？"

## Step 6 — 人工确认

等待用户明确回复，处理三种情况：

**用户确认**（"没问题"、"就这样"）→ 进入 Step 7

**用户局部调整**（"流程第 3 步不对"、"去掉 ins-pay"）→ 更新建议后再次展示，确认后进入 Step 7

**用户否定整体**→ 询问具体原因，重新分析输出新建议

**在用户明确确认之前，不写入任何文件。**

## Step 7 — 写入 02-服务拆分.md，返回摘要

### 写文件规则

1. 读取模板：`~/.claude/skills/service-split/assets/service-split-template.md`
2. 按八节结构填充所有内容，不得省略任何节
3. 写入输出目录的 `02-服务拆分.md`

**各节填充要点**：

| 节 | 填充要点 |
|----|---------|
| 一、功能清单摘要 | Step 1 提取的功能点，每行一条 |
| 二、全局业务流程 | Step 2 梳理的触发点、端到端时序（含服务介入步骤）、**Mermaid sequenceDiagram**、关键数据流、异常路径 |
| 三、服务边界定义 | 每个服务一个子节，含本地仓库状态、职责、包含/不包含、对外暴露、依赖上游、知识库依据 |
| 三·五、功能点归属表 | 功能点→主责服务映射表 + 冲突检测三项结果；有冲突时说明解决方案 |
| 四、本次各服务改动清单 | 以服务为维度，每个服务一个子节，含本地仓库状态、角色、改动类型表；⚠ 仓库未找到时追加核实提醒 |
| 五、服务改动总览 | 汇总表：服务名、本地仓库状态、角色、改动量级、备注 |
| 六、知识库空白 | 无依据的功能点，处理方式填"已人工确认"或"待人工确认" |
| 七、变更记录 | 初始版本 + 日期 + "已人工确认" |

### 产出文件末尾的「小结」段落（必写）

在 `02-服务拆分.md` 末尾追加 `## 小结` 段落，3 个固定 bullet。独立运行时也写（作为阶段文档小结，非 dev-workflow 专属）：

```markdown
## 小结

- 产出: {文件清单，逗号分隔，如 workflow/XX/02-服务拆分.md}
- 阻塞: {无，或简述；如"⚠️ 服务 X 本地仓库未找到，需先 clone"}
- 交接: {一句话，下一阶段必须知道的；如"主责 ins-user、协同 ins-trade，主项目路径 /path"}
```

**字段规则**：
- `产出`：本阶段产出的所有文件路径
- `阻塞`：未找到本地仓库的服务、知识库空白等待确认项；无则写"无"
- `交接`：主责服务路径 + 关联服务列表 + scaffold 分流关键信息（一句话）；dev-workflow scaffold 分流从正文"五、服务改动总览"读取 services 数组（含 name/path/role/repo_status/modules），小结只做一句话提示

### 面向用户的结束语

> 服务拆分完成，文档已保存到 {路径}。共涉及 {N} 个服务，全局业务流程见文档第二节，各服务改动清单见第四节。

## 与 dev-workflow 的集成

- `service-split` 负责生成 `02-服务拆分.md`，完成人工确认，返回摘要
- `dev-workflow` 负责收到摘要后更新 `current.md`（关联项目字段、当前阶段、待办）
- `dev-workflow` 负责决定是否进入技术方案阶段

如果由 `dev-workflow` 调用，优先遵循它传入的目录、需求名称和主项目路径，不再单独询问。
