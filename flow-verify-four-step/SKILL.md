# 先跑通，再四步法

口径只此一份。新的判定标准追加到下面，不另起一套。

## 顺序

1. 先跑通主流程。主流程没有按用例走绿之前，不铺异常矩阵，不宣称覆盖。
2. 主流程绿了之后，再按四步法把正常场景和异常场景都做成用例并执行。
3. 一条链路四步做完，才可以说这条链路覆盖了。
4. 走到复盘或知识库更新时，把这次可复用的经验追加到本文「经验」一节，并在同一次验证里用上，不等下一次需求。

编码的人写的方案，不在同一轮里自己审查放行。human 门（配置里 gate=human）不停。

## 四步法

1. 数据准确性：证书、身份、订单、金额、状态、时间这类业务数据，不能只看接口成功。必须把报文、库表、上下游对到字段级。对不上就是 bug，即使流程跑通。
2. 规范与日志：协议字段、枚举、必填、时间合法性、日志能否定位，都是验收标准。不达标就认定为 bug。日志只打异常类名、丢掉状态码和响应体，算 bug。环境问题只解释某次失败，不替代规范不达标。
3. 错误不得内部吞掉：该抛的异常被 catch 后返回成功、空值或另一个业务码，调用方无法区分原因，算 bug。失败要带着原因出去，或在日志里留下可定位的状态码、响应体和消息。
4. 新的判定标准追加到同一条，不另起口径。

通用验证流程（一条链路按这四步做完再宣称覆盖）：

1. 先整理测试用例。从方案抽出主流程、状态和异常，落成用例，再动手。
2. 用改数据、造数构造场景。只动测试库，记下原值，测完改回。
3. 按用例验证。报文、库表、上下游对到字段，不只看成功码。
4. 缓存和异常单独成条。缓存命中、负缓存、缓存不挡住后续状态；下游失败、非法报文、错误被吃掉。

## 怎么做

- 用例从方案和提测清单抽，先落表再执行。每条写清入口、造数、期望字段、测完如何改回。
- 只动临时目录或测试库。改配置前留下原值，测完改回并复核原值。
- 通过要同时看到退出码或状态码、关键字段、关键原文。退出码单独不算环境通过。
- 阻塞提示和失败分开记。退出码 0 且带阻塞标记，不算失败，也不算没看见。
- 黑盒先打对外入口。不靠读实现下结论。
- 发现阻断级缺陷就停主流程，立单，不在验证方自己改实现。
