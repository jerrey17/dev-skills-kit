**风险评估**

_服务发布流程风险_
- [ ] 多服务变更已明确发布顺序及依赖关系（先后/并行），接口兼容窗口已标注
- [ ] 发布期间新旧版本共存场景已评估（接口向前兼容 / 双读双写 / Feature Flag）
- [ ] 每个发布步骤均有可独立回滚的方案，回滚后不产生脏数据或状态不一致
- [ ] 涉及数据库变更的发布步骤，DDL 与代码发布顺序已明确（先 DDL 后代码 or 反之），且兼容反序回滚

_代码改动风险_
- [ ] 改动涉及的公共方法/组件已做影响范围分析（GitNexus impact），高风险调用方已列出
- [ ] 行为变更（默认值/枚举扩展/返回结构）对已有调用方的兼容性已评估，不兼容处有过渡方案
- [ ] 改动涉及并发热点代码时，已评估锁/CAS/队列等并发控制变更对吞吐与死锁的影响
- [ ] 配置项变更（新增/改名/改默认值）已纳入配置项清单，且旧值→新值平滑过渡

_数据风险_
- [ ] 数据迁移/刷数有明确的执行计划（批次大小、并发、幂等、校验、回滚 SQL）
- [ ] 新旧数据格式兼容（代码先兼容旧格式→刷数→移除旧格式兼容），不存在发布窗口内读到不可解析数据的场景
- [ ] 涉及资金/账务数据的变更，已设计对账/勾兑校验点，异常时有告警+人工介入机制
- [ ] 逻辑删除 / 状态变更类操作可追溯（有操作日志或 binlog 保留策略），误操作可恢复

**测试**
- [ ] 每功能点：正常 + 幂等/并发 + 异常/边界 + 灰度开关
