# Java Code Review（基于团队 java代码规范）

## 使用场景

- 当用户请求对 **Java 代码** 或 **Java 相关 PR/变更** 进行 code review 时使用本 Skill。
- 当前项目属于支付/信贷相关工程，review 时必须遵守项目中的 `java代码规范` 文档（`pay/resources/java代码规范.md`）。
- cr 某路径下的代码，例如 cr liviea 项目的代码，路径：`/path/to/project`。
- 当用户说「cr 最近提交的代码」「cr 最近几次提交」「看下最近改动」时，默认以 **当前仓库最近一次或最近 N 次 commit 的 diff** 为主要审查对象（使用 `git diff HEAD~1..HEAD` 或用户指定的范围）。
- 当用户按**时间区间**发起请求（例如：「从 2026-03-01 截止到现在提交的代码进行 CR」），应：
  - 使用 `git log --since="2026-03-01" --until="2026-03-10"`（实际以当前日期或用户给定截止时间为准）确定 commit 范围；
  - 使用对应范围的 `git diff <old_commit>..<new_commit>` 生成增量改动；以这段时间内的 **Java 相关改动** 作为主要审查对象。

## 总体原则

在 review Java 代码时，默认你已经熟悉 Java 语言和常见最佳实践。本 Skill 的目标是让你**优先按照团队规范**审查，并在反馈中显式指出与规范的对应关系。

- **优先团队规范，其次通用经验**：若通用经验与 `java代码规范` 不一致，以文档为准。
- **问题分级**：将发现的问题分为：
  - **[严重问题]**：违反「强制」要求、可能导致 Bug、安全问题、数据错乱、并发问题、事务/异常处理错误等，必须修改。
  - **[一般问题]**：违反「推荐」要求或明显影响可读性、维护性，应当修改。
  - **[优化建议]**：风格/结构优化，不影响正确性，可酌情采纳。
- **引用规范条款**：尽量在每条问题后用简短文字标出关联条款，如：
  - `（对应：3.1 命名风格 第 5 条 抽象类以 Abstract 开头）`

## Review 步骤

按以下流程进行 Java 代码 review，并用结构化输出反馈：

1. **理解变更背景**
   - 简要说明你从代码中推断的功能目的和改动范围（不用向用户要额外上下文，直接基于代码本身推断）。
   - 若用户未提供具体文件而是说「最近提交」：
     - 优先基于 `git diff` 的改动范围来推断本次变更的功能点；
     - 明确指出本次 review 关注的是「最近一次/最近 N 次提交的增量变更」，而不是整个仓库全量代码。
   - 若用户按「起止时间」说明范围（如「从 2026-03-01 截止到现在」）：
     - 先基于时间区间定位 commit 列表（如 `git log --since=... --until=...`）；
     - 再根据首尾 commit 做一次整体 diff，或按 commit 逐个 review，并在反馈中写明「本次 review 范围 = [起始 commit] ~ [结束 commit]，对应时间区间」。

2. **按规范维度逐项检查**
   审查时，按照 `java代码规范` 中的主要章节分维度检查，至少覆盖：
   - **项目结构与分层**
   - **命名与常量定义（3.1、3.2）**
   - **编码风格与编码规约（3.3、3.4）**
   - **控制语句与集合处理（3.5、3.6）**
   - **并发处理（3.7）**
   - **注释规范（3.8）**
   - **异常处理与日志（4.x、6.2）**
   - **组件使用与接口规范（5.x、6.3、6.4 等，若代码涉及）**

3. **形成结构化问题清单**
   - 将发现的问题按「严重问题 / 一般问题 / 优化建议」分组列出。
   - 每条问题至少包含：
     - **位置**：类名 / 方法名 / 代码片段特征，若有行号则写明（行号可以用户提供的为准）。
     - **问题描述**：简明准确说明问题是什么。
     - **违反的规范或风险说明**：指出对应章节或简短解释风险。
     - **修改建议**：给出具体改法或推荐写法。

4. **正向反馈与总体评价**
   - 可以简要指出做得好的地方（例如命名清晰、异常封装合理、线程池使用规范等）。
   - 最后给一个总体评价和合并建议（如「整体符合规范，少量风格问题」「存在多处强制规范问题，建议修改后再合并」）。

## 重点检查维度与常见问题提示

### 1. 目录结构与分层

当看到包名结构或类职责时，检查是否与规范一致：

- 代码应按 `config/constant/domain/enums/exception/mapper/model/route/controller/service/utils/job/depend` 等职责分包。
- 注意避免「大而全」的 `common` 包；如果看到类似 `common/util`、`common/service` 汇聚大量无关逻辑，应指出问题并建议拆分。

### 2. 命名与常量（对应 3.1、3.2）

在命名上重点检查：

- 类名、方法名、参数名、成员变量、局部变量是否遵循驼峰命名，类名首字母大写。
- 常量是否全部大写并使用下划线，如 `MAX_RETRY_TIMES`。
- 是否存在下划线或 `$` 开头/结尾的变量名，如 `_userName`、`name$`（应判为违反强制规范）。
- 抽象类是否以 `Abstract` 开头，异常类是否以 `Exception` 结尾，工具类以 `Util` 结尾，枚举以 `Enum` 结尾。
- 布尔字段是否错误地以 `is` 前缀命名（会影响序列化/反序列化）。
- 是否使用了难以理解的缩写或单字母命名（如 `int a = 1;`），对于业务变量应建议使用完整单词组合。
- long 常量是否以大写 `L` 结尾。

### 3. 编码风格与规约（对应 3.3、3.4）

重点关注：

- 所有 `if/else/for/while/do` 是否都使用大括号，不允许单行省略大括号。
- 关键字与括号之间是否有空格，如 `if (condition)`。
- 运算符两侧是否有空格，参数逗号后是否有空格。
- 是否存在「魔法值」，明明是固定含义却直接写常量（如 `100`、`7`），应建议提取为常量或枚举。
- `equals`/包装类型比较写法是否安全：
  - 是否避免 `object.equals("xx")` 这种可能 NPE 的写法；
  - 是否避免用 `==` 比较包装类型或字符串；推荐使用 `equals` 或 `Objects.equals`。
- 循环中是否频繁字符串拼接，建议改为 `StringBuilder`。
- 访问 `split` 结果数组时是否考虑长度与尾部空项问题。
- 是否合理使用 `final` 修饰不可变引用、常量、局部变量等。

### 4. 控制语句与集合处理（对应 3.5、3.6）

- `switch` 语句：
  - 每个 `case` 是否都有 `break/return` 或清晰注释说明「意图贯穿」；
  - 是否存在 `default` 分支且位于末尾。
- `if-else` 是否层级过深（>3 层）且可以通过早返回、策略模式等简化。
- 循环中是否进行了不必要的对象创建、连接获取、重复 try-catch 等。
- 集合处理：
  - 是否在 `foreach` 中对集合执行 `add/remove` 等结构修改（违反强制规范，应改用 `Iterator`或其他安全方式）。
  - 是否错误地对 `Arrays.asList()` 得到的集合执行 `add/remove/clear`。
  - 初始化集合/Map 时是否考虑初始化容量，避免无节制扩容。
  - 遍历 `Map` 是否优先使用 `entrySet` 而非 `keySet` + `get`。

### 5. 并发处理（对应 3.7、6.1.2 等）

若代码涉及多线程、线程池、共享状态，重点检查：

- 单例对象、工具类、工厂、缓存等是否线程安全。
- 是否使用 `ThreadPoolExecutor` 而不是直接 `new Thread` 或 `Executors` 静态工厂。
- 是否存在粗粒度锁（如给整个类加锁）或加锁顺序不一致导致潜在死锁。
- 是否对同一记录/对象的并发修改采取了合适的锁或乐观锁机制。
- 是否正确使用日期时间 API，避免 `static SimpleDateFormat` 等非线程安全写法。
- 若使用 `ThreadLocal`，是否注意及时 `remove()`，避免内存泄漏和脏数据。

### 6. 注释规范（对应 3.8）

- 类、属性、方法是否使用 Javadoc 风格注释 `/** ... */`，而不是简单 `//`。
- 是否有重要公共类缺少创建者与创建日期说明（若团队已有此约定）。
- 方法内的单行注释是否独立成行，用 `// ` 开头（双斜线后一个空格），多行注释是否对齐。
- 枚举项是否有注释解释用途。
- 是否存在过时注释、已变更逻辑却未同步更新的注释。
- TODO 注释是否写清楚原因和后续处理方向。

### 7. 异常处理与日志（对应 4.x、6.2）

对于异常处理和日志，是 review 的高优先级：

- 是否通过**预检查**避免常见运行时异常（如 NPE），而不是大范围 try-catch。
- 对外 HTTP/API 接口是否将异常转换成统一的错误码/错误信息返回，而不是直接向外抛出框架异常或打印堆栈给客户端。
- try-catch 范围是否过大，是否只包裹必要代码。
- 是否在 finally 中做资源关闭，且避免在 finally 中 `return`。
- 是否错误地使用异常控制正常流程逻辑。
- 事务代码是否在 catch 后有正确回滚逻辑。
- 日志：
  - 生产环境是否误用 `debug` 日志或打印 SQL；
  - 是否出现重复打印同一个异常堆栈；
  - 是否确保重要日志打印了业务幂等 ID / 单号 / traceId 等，且避免将敏感信息明文输出；
  - 告警是否有合理收敛 key，避免告警风暴。

### 8. 组件与接口规范（对应 5.x、6.3、6.4 等）

当代码涉及组件依赖或接口定义时，重点关注：

- fastjson、sharding-jdbc、数据库连接池、redis 客户端等组件的版本与使用方式是否安全、可靠。
- 是否误用个人 GitHub 开源组件在生产环境中。
- Saturn、分布式调度等组件是否正确处理分片、并发以及线程使用。
- MyBatis 批量插入是否错误依赖「通用字段列表」，而不是固定字段列表，避免公共字段变更引发生产问题。
- pb 协议消息定义是否：
  - 使用小写加下划线命名；
  - 新增字段时保证索引位自增且不与旧字段冲突；
  - 请求/响应包含默认 basic 字段；
  - 在业务代码中是否先转换为可读性更高的 model 对象再做业务处理。

## 输出格式要求

每次 Java code review，使用如下 Markdown 模板输出（可按实际情况删掉空段落）：

```markdown
### 功能与变更概述
- 简要说明你理解的本次改动目的与范围。

### 严重问题（必须修改）
1. [位置] 问题描述  
   - 原因/风险：...  
   - 规范引用：对应 3.x/4.x/6.x 条款（可简写）  
   - 修改建议：...

### 一般问题（建议修改）
1. [位置] 问题描述  
   - 原因/影响：...  
   - 规范引用：...  
   - 修改建议：...

### 优化建议（可选）
1. [位置] 建议内容  
   - 原因：...  
   - 建议做法：...

### 正向反馈与总体评价
- 优点：列出 1~3 点亮点（例如：命名清晰、异常封装合理、日志信息充分等）。
- 总体建议：是否建议当前版本可合并，如「建议修复严重问题后再合并」或「整体符合规范，仅有少量风格类建议」。
```

在给出反馈时，务必：

- **优先指出违反强制规范的问题**；
- **明确指出对应的规范条款或章节**（可以是简短文字描述，无需逐字复制原文）；
- 给出**可操作的修改建议**，而不是只说「这里不规范」。

## 产出文件末尾的「小结」段落（必写）

将审查结论写入 `05-代码审查.md`，并在文件末尾追加 `## 小结` 段落，3 个固定 bullet。独立调用时也写（作为审查文档小结，非 dev-workflow 专属）：

```markdown
## 小结

- 产出: {文件清单，如 workflow/XX/05-代码审查.md}
- 阻塞: {无，或简述；如"3 个严重问题待修复后才能合并"}
- 交接: {一句话，下一阶段必须知道的；如"严重问题已修复，建议合并，可进入测试阶段"}
```

**字段规则**：
- `产出`：本阶段产出的所有文件路径
- `阻塞`：未修复的严重/一般问题数；无则写"无"
- `交接`：合并建议（可合并/建议修复后合并/不建议合并）+ 已修复情况（一句话）
